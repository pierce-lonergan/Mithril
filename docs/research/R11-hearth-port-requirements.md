# R11 — Hearth deep read and Mithril port requirements

*Scope: a read-only deep read of the local Hearth clone (working tree with uncommitted R3 changes, base commit `b5d3f14`), turned into what Mithril must be able to express so that Hearth can be ported with zero performance loss and zero output change. Hearth links below point at `github.com/pierce-lonergan/hearth/blob/main/...`. Line numbers are from the local working tree. For the 17 files with uncommitted changes (model.c, pool.c, quant.c, api.c, the platform files, hearth.h, hx_model.h, hx_platform.h, hx_pool.h, engine.py, among others) the GitHub anchors can point a few lines off. Web search was unavailable during this task (the shared search budget was used up), so the few external facts come from official pages fetched directly. Everything else comes from the repository.*

## Summary

- **Hearth is small but dense.** The engine is 9,068 lines of C11: 8,827 in `engine/src` plus `engine/include`, and a 241-line benchmark tool. Its C tests run to 14,859 lines. On top sit 9,042 lines of numpy-only Python (the brief's figure of "~6k" is low) and 4,822 lines of stdlib-only governance tools ([README](https://github.com/pierce-lonergan/hearth/blob/main/README.md), [CMakeLists.txt](https://github.com/pierce-lonergan/hearth/blob/main/CMakeLists.txt)). The forward pass in `model.c` is 2,040 lines. The rest is kernels (1,408 lines), the store (1,030), the container parser (922), the pool (732) and the platform layer (1,574).
- **The hardest requirement is semantic, not about speed.** The scalar C code *is* the numeric definition, and every SIMD kernel must reproduce it bit for bit. That means no FMA contraction, a fixed 16-lane-then-tree reduction, exact int32 block sums, rank-order expert sums, one canonical NaN, and libm calls made "the same way from every code path" ([NUMERICS.md](https://github.com/pierce-lonergan/hearth/blob/main/docs/NUMERICS.md), [quant.c:1-8](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L1)). Mithril needs *order-preserving* vectorisation as a language guarantee. "Vectorise everything" (seed B6) is the wrong goal.
- **Decode is already close to the DRAM roofline.** [inference] From the container layout, one Qwen3-30B-A3B Q4/Q8 decode token touches about 2.38 GB: 0.96 GB of experts, 1.31 GB of dense weights and LM head, and about 0.11 GB of KV. The measured 21.88 tok/s fully cached ([H03-forward-gen-002](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/H03-forward-gen-002.json)) is therefore about 52 GB/s. Hearth's own machine profile puts this PC at about 78 GB/s AIDA64 read and assumes about 60 GB/s for streaming kernels ([hardware.py:77-83](https://github.com/pierce-lonergan/hearth/blob/main/python/hearth/sim/hardware.py#L77)). No language can give a large speed-up on fully cached decode. The open headroom is in prefill and attention compute, in I/O–compute overlap, and in bytes per token.
- **The C ABI in `hearth.h` is the acceptance boundary.** It has 19 exported functions and 3 structs, and the golden suite drives the engine only through Python ctypes mirrors of those structs ([hearth.h](https://github.com/pierce-lonergan/hearth/blob/main/engine/include/hearth.h), [engine.py:30-153](https://github.com/pierce-lonergan/hearth/blob/main/python/hearth/engine.py#L30), [test_golden_invariants.py](https://github.com/pierce-lonergan/hearth/blob/main/tests/golden/test_golden_invariants.py)). A Mithril engine that exports the same ABI keeps the whole Python toolkit and every golden test working unchanged.
- **The golden tests are necessary but not sufficient to prove "zero output change".** They check self-consistency (threads, cache, ISA, batching) and tolerance against the numpy reference. They do not check bit equality with the C binary. A port with a different but internally consistent float order would pass them. The port needs an additional cross-binary oracle: hashes of C-engine logits and quantiser bytes. Hearth already used this technique once, comparing SHA-1 hashes of logits over 512 real-weight steps ([policy-default.md:53](https://github.com/pierce-lonergan/hearth/blob/main/docs/results/policy-default.md#L53)).
- **The libm is part of the output.** `expf`, `sinf`, `cosf` and `sqrtf` come from the platform libm and are called through volatile function pointers so that no compiler can fuse or vectorise them ([quant.c:653-666](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L653), [model.c:219-235](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L219)). This guard exists because Apple clang's sincos fusion broke bit-identity on macOS ([ci-first-runs.md](https://github.com/pierce-lonergan/hearth/blob/main/governance/reviews/2026-10-05-ci-first-runs.md)). To be bit-identical to C, Mithril must call the *same* CRT symbols as opaque FFI calls.
- **The platform layer needs systems-programming primitives on every OS.** These are positional direct I/O (Windows `FILE_FLAG_NO_BUFFERING` + `FILE_FLAG_OVERLAPPED` with per-request events; `O_DIRECT` and `F_NOCACHE` on POSIX), large-page arenas, SRW locks and condition variables with timed waits that never return early, C11 atomics with explicit orderings, cache-line-padded layout, and cpuid/XCR0 detection ([platform_win.c](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_win.c), [platform_posix.c](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_posix.c), [pool.c](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/pool.c)).
- **Several governance practices map onto language features.** Hearth enforces invariants, sealed golden tests, mutation testing, typed handovers, file ownership and measured-versus-simulated honesty with external Python tools. Its own record shows where that leaks. A ctypes mirror drifted and caused an 8-byte overflow ([ci-first-runs.md:14](https://github.com/pierce-lonergan/hearth/blob/main/governance/reviews/2026-10-05-ci-first-runs.md#L14)). The default heat decay moved to 0.9 while ADR-0004 and `hx_store.h` still say 0.995. In the handover schema, `kind: measured|simulated` is optional. Each of these could be a compile-time check in Mithril.
- **Port plan.** Port bottom-up behind Hearth's internal headers (`hx_*.h`) in a strangler-fig pattern: kernels → parser → pool → store and I/O → forward → API. At every step, link the Mithril module into the C engine and gate it on the C test suites, the golden suite and the cross-binary hash oracle.
- **The port collides with Hearth's own constitution.** INV-DEP says the core is "C11 + OS APIs only" ([INVARIANTS.md](https://github.com/pierce-lonergan/hearth/blob/main/governance/INVARIANTS.md)), so a Mithril core needs a maintainer ADR superseding ADR-0001 and an invariant change, which trips Hearth's circuit breaker.

### 2. Numerics contract (what "zero output change" means)

- **FMA contraction is banned.** The build uses MSVC `/fp:precise` and GCC/Clang `-ffp-contract=off`, and never `-ffast-math` ([NUMERICS.md:10-13](https://github.com/pierce-lonergan/hearth/blob/main/docs/NUMERICS.md#L10), [CMakeLists.txt:54,57](https://github.com/pierce-lonergan/hearth/blob/main/CMakeLists.txt#L54)). Both flags matter. Clang's default for C is `-ffp-contract=on`, which fuses within a statement ([Clang manual](https://clang.llvm.org/docs/UsersManual.html)). MSVC's `/fp:precise` stopped generating contractions only in Visual Studio 2022; earlier versions could contract by default ([MS /fp docs](https://learn.microsoft.com/en-us/cpp/build/reference/fp-specify-floating-point-behavior)). The SIMD files use separate mul and add intrinsics everywhere ([quant_avx2.c:9](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx2.c#L9), [quant_avx512.c:10](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx512.c#L10)). The ISA-free `quant.c` is compiled "without ISA flags, so the compiler cannot emit FMA" ([quant.c:7](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L7)).
- **Reductions follow a fixed order.** `sum16`/`dot16` use 16 lanes `L[i&15]`, then a tree with s = 8, 4, 2, 1 ([NUMERICS.md:18-23](https://github.com/pierce-lonergan/hearth/blob/main/docs/NUMERICS.md#L18), [quant.c:604-624](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L604)). One AVX-512 register holds exactly the 16 lanes, and AVX2 uses two registers ([quant_avx512.c:34-43](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx512.c#L34), [quant_avx2.c:35-41](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx2.c#L35)).
- **Quantised matmuls split exact integer work from fixed float work.** The integer part is exact: `isum` per 64-block, computed with Q4 `Σnib·x − 8·Σx`, VNNI `vpdpbusd` on biased unsigned weights, or AVX2 `maddubs`/`madd` with a written int16 no-saturation proof ([NUMERICS.md:40-50](https://github.com/pierce-lonergan/hearth/blob/main/docs/NUMERICS.md#L40), [quant_avx2.c:224-230](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx2.c#L224), [quant_avx512.c:236-241,266-272](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx512.c#L236)). The float part is fixed per block: `acc + (float)isum * (dw*dx)`. SIMD lanes are independent rows, so lane order never enters a float sum. [inference] Integer arithmetic gives a code generator full freedom to reorder; float arithmetic gives it none. A language can encode exactly this split.
- **Canonical NaN.** Every NaN kernel output is stored as `0x7fc00000`, because IEEE 754 does not fix which NaN propagates and compilers commute SIMD operands ([NUMERICS.md:56-58](https://github.com/pierce-lonergan/hearth/blob/main/docs/NUMERICS.md#L56), [quant.c:53-65](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L53), [quant_avx512.c:26-28](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx512.c#L26)).
- **Batch equals sequential.** Every (token, row) of `Y = W·X` must equal the T=1 value ([hx_quant.h:49-57](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/hx_quant.h#L49)). Attention for each token uses single-token arithmetic over its causal prefix. Experts write per-(token, rank) buffers that are summed in rank order ([model.c:9-24](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L9), [model.c:937-957](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L937)).
- **Rounding tricks assume the default FP environment.** `q_rint` uses the 1.5·2²³ magic-number trick, and the SIMD `cvtps_epi32` relies on round-to-nearest-even in MXCSR ([quant.c:44-49](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L44), [quant_avx2.c:100](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx2.c#L100)). Software f16/bf16 conversions are bit-exact copies of F16C behaviour ([quant.c:16-35](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L16), [platform_common.inc:21-77](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_common.inc#L21)).
- **Bit-identity is scoped to a fixed binary and ISA.** INV-DET-1 is defined "for a fixed binary and ISA" ([INVARIANTS.md:11](https://github.com/pierce-lonergan/hearth/blob/main/governance/INVARIANTS.md#L11)). Across operating systems, libm differences are allowed. [inference] So "zero output change" for Mithril has two parts: bit-identical to the C binary on the same OS, CRT and ISA, and passing every golden test.
- **External drift risk.** glibc 2.42 adopted 30 correctly rounded binary32 functions from CORE-MATH. `expf`, `sinf` and `cosf` are not among them, though CORE-MATH links patches for them ([CORE-MATH](https://core-math.gitlabpages.inria.fr/)). [inference] A future libm update could change Hearth's logits on Linux even for the unchanged C engine.

### 3. Hot paths and their roofline character

All numbers are measured unless marked otherwise, on the Ryzen 9 9950X box, with the machine shared as each source notes (INV-HONEST).

1. **Quantised matvec/matmul kernels.** AVX-512 `qtile16`, with `qtile4` for row tails, and AVX2 `qtile8`. The T=1 decode path keeps one accumulator register per 16-row tile. The T>1 path processes 8 tokens per pass over a tile ([quant_avx512.c:274-306](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx512.c#L274)). One thread reached 69.6 GB/s of weight bytes for AVX-512 Q4 at T=1 with L2-resident data, on a busy machine ([T02-kernels-gen-002](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/T02-kernels-gen-002.json)). Decode is **DRAM-bandwidth-bound**. [inference] 21.88 tok/s × ~2.38 GB/token ≈ 52 GB/s against ~60–78 GB/s achievable. Prefill is **neither bound**. 512-token prefill runs at 345–433 tok/s ([H03-forward-gen-001](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/H03-forward-gen-001.json)). [inference] At about 2 × 3 G int8 ops per token that is roughly 3 TOPS, against the ~20 TOPS VNNI peak in Hearth's profile ([hardware.py:83](https://github.com/pierce-lonergan/hearth/blob/main/python/hearth/sim/hardware.py#L83)). The roadmap's expert-major tiled VNNI/AMX prefill (task R05) targets this gap.
2. **Activation quantisation** (`act_q8_*`, once per matmul input) and the fused SwiGLU-plus-quantise in `swi_range` ([model.c:453-462](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L453)). Light and bandwidth-bound.
3. **Attention core.** Scores use the F32 kernel (`dot16`), softmax uses `expf`, and the value pass is a portable `restrict` loop that the compiler vectorises across output dims ([model.c:490-504, 581-609](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L490)). The value pass runs at 18.0 GMAC/s. A bit-identical AVX-512 register-blocked prototype runs at 94 GMAC/s and is not yet in the engine ([H03-forward-gen-001](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/H03-forward-gen-001.json)). This path is **compute- and latency-bound** and grows with context: 2,048-token prefill runs at 226 tok/s against 384 at 512 tokens ([H03-forward-gen-002](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/H03-forward-gen-002.json)). This is the clearest place where better code generation pays off without touching the canonical order.
4. **MLA latent projection** (`mla_qlat`: dequantise a W_UK row, then a scalar multiply-add loop) and `mla_out` ([model.c:685-706, 752-771](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L685)). Compute-bound and only partly vectorised. It matters for DeepSeek/Kimi-class models.
5. **Expert I/O.** Reader threads issue one `pread` per slab, outside the store mutex ([store.c:340-382](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/store.c#L340)). Peak cold demand reads reach 7.16 GB/s with 2.39 MiB slabs, and prefetch batches 6.72 GB/s, on a Samsung 990 PRO ([H01-store-gen-001](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/H01-store-gen-001.json)). This is **NVMe-bandwidth-bound**. With a 2 GiB cache the real model reads 401 MB/token and decodes at 13.02 tok/s ([R3-forward-gen-001](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/R3-forward-gen-001.json)). [inference] The bounds are 9.9 tok/s with no overlap (0.401/6.5 + 2.38/60 s) and 16.2 tok/s with perfect overlap, so overlap is partial. Kimi-K2 slabs are 22.3 MiB, so a cold token reads about 11 GB. [inference] At about 6.5 GB/s that is roughly 1.7 s, consistent with the measured 1.2–1.8 s/token worst case ([README](https://github.com/pierce-lonergan/hearth/blob/main/README.md)).
6. **Pool dispatch.** A token runs hundreds of regions. A 16-thread round trip takes about 0.75 µs and a 32-thread one about 7.5 µs, both measured under load ([H02-platform-pool-gen-003](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/H02-platform-pool-gen-003.json)). Batches under 256 tokens therefore use physical cores only, and small regions stay on the caller, sized by an estimate of 6 µs minimum work and one thread per 3 µs ([model.c:53-72, 279-287](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L53)). This path is **latency-bound**.
7. **Routing, norms and sums.** Routing uses an O(K·E) selection scan ([model.c:825-865](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L825)). Rmsnorm uses the scalar `dot16` and `expf`-based activations. Each is small but strictly ordered.

### 4. Capabilities Mithril needs (zero performance loss, zero output change)

**P0 — without these the port cannot be bit-identical or fast**

1. **Strict IEEE binary32 by default.** No contraction, reassociation, FTZ/DAZ or fast-math. Rounding at each operation, also inside vector types. Needed for the separate mul/add pairs in all kernels and for `value_sum` ([NUMERICS.md:10-13](https://github.com/pierce-lonergan/hearth/blob/main/docs/NUMERICS.md#L10)).
2. **Canonical reduction order as a declared semantic**, such as `reduce<16, tree>`, that the compiler must preserve and the SIMD backend must map onto 1×zmm or 2×ymm ([quant.c:604-624](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L604)).
3. **Explicit fixed-width SIMD types and intrinsics** for 128, 256 and 512 bits: `maddubs`, `madd`, `vpdpbusd`, `cvtph2ps`, `permutevar8x32`, `shuffle_i64x2`, `inserti64x4`, `packs`, `hadd`, `blendv`, `cvtepi32_epi8` ([quant_avx2.c:224-320](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx2.c#L224), [quant_avx512.c:189-272](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx512.c#L189)).
4. **AVX-512 opmask types and masked operations:** `maskz_loadu` tails, `mask_add`, `mask_mov` for NaN canonicalisation, `mask_storeu`. AVX2 needs `maskstore` ([quant_avx512.c:119-155, 313, 338](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx512.c#L119), [quant_avx2.c:235, 267](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx2.c#L235)).
5. **Per-function target features plus runtime ISA dispatch.** Function tables are chosen once, cached in an atomic with acquire/release, and can be overridden by environment variable. Detection checks cpuid together with XCR0 OS-state ([CMakeLists.txt:37-46](https://github.com/pierce-lonergan/hearth/blob/main/CMakeLists.txt#L37), [quant.c:443-501](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L443), [platform_common.inc:108-161](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_common.inc#L108)). Kernels for every ISA must coexist in one binary.
6. **Exact integer SIMD semantics with checkable range proofs.** For example, AVX2 pairs ≤ 2·15·127 cannot saturate int16 ([quant_avx2.c:224-230](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx2.c#L224)). Mithril should verify such bounds statically. Integer reassociation stays free.
7. **Opaque calls to the platform libm.** No builtin folding, inlining, vectorising or sincos fusion ([quant.c:653-666](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L653), [model.c:219-235](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L219)).
8. **Exact layout control and a stable C ABI.** Packed 66/34/72-byte blocks with static size asserts ([hx_quant.h:22-28](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/hx_quant.h#L22)). Unaligned loads done as bit-casts ([quant_avx2.c:57-61](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx2.c#L57)). Explicit little-endian decoding ([modelfile.c:50-60](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/modelfile.c#L50)). `extern "C"` exports with `__declspec(dllexport)` on Windows and default visibility elsewhere ([hearth.h:24-34](https://github.com/pierce-lonergan/hearth/blob/main/engine/include/hearth.h#L24), [CMakeLists.txt:75](https://github.com/pierce-lonergan/hearth/blob/main/CMakeLists.txt#L75)). Struct layouts must match ctypes ([engine.py:30-91](https://github.com/pierce-lonergan/hearth/blob/main/python/hearth/engine.py#L30)). Calling conventions must match Win64, SysV and AArch64.
9. **No hidden runtime.** No GC, no unwinding across the ABI, no required global initialisation. Lazy one-time init is thread-safe (`InitOnceExecuteOnce`, `pthread_once`). Errors come back as negative codes and bad input never crashes ([api.c:5-8](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/api.c#L5), [platform_win.c:621-640](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_win.c#L621)). The single deliberate `abort` is pool misuse ([pool.c:659-663](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/pool.c#L659)).
10. **Aligned and large-page memory.** 64-byte aligned heap allocations. Arenas from `VirtualAlloc`/`mmap`, with `MEM_LARGE_PAGES` after enabling `SeLockMemoryPrivilege` through runtime-resolved advapi32, or THP via an over-mapped 2 MiB-aligned `mmap` plus `madvise` ([platform_win.c:79-135](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_win.c#L79), [platform_posix.c:53-82](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_posix.c#L53)). The slot arena is `n_slots × slab_bytes` and 4096-aligned ([store.c:945-952](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/store.c#L945)).
11. **Positional direct I/O.** Windows handles are opened `FILE_FLAG_OVERLAPPED | FILE_FLAG_NO_BUFFERING`, with a sector-size check, a recycled per-request event and 1 GiB chunking. A synchronous handle measured 0.62 GB/s against 5.73 GB/s overlapped at 16 threads ([platform_win.c:313-463](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_win.c#L313), [hx_platform.h:133-137](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/hx_platform.h#L133)). POSIX uses `O_DIRECT` with a buffered fallback, `F_NOCACHE` on macOS, and EINTR loops ([platform_posix.c:299-380](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_posix.c#L299)). Windows requires sector-multiple sizes and offsets and sector-aligned buffers ([MS file buffering](https://learn.microsoft.com/en-us/windows/win32/fileio/file-buffering)). Mithril should be able to check the 4096 alignment of buffer, offset and size in types.
12. **Threads, mutexes and condition variables** with monotonic timed waits that never time out early (Windows re-waits after an early millisecond expiry; Linux uses `CLOCK_MONOTONIC` condattr; macOS uses relative waits) ([platform_win.c:281-309](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_win.c#L281), [platform_posix.c:247-280](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_posix.c#L247)). Thread stacks must be at least 1 MiB ([platform_posix.c:160-162](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_posix.c#L160)).
13. **C11-equivalent atomics.** Relaxed, acquire, release and seq_cst orderings; weak CAS; `fetch_add`/`fetch_sub` on 32- and 64-bit values; `atomic_flag`. The pool's lock-free sleep handshake depends on seq_cst store/load ordering ("at least one side sees the other") ([pool.c:13-19, 286-354](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/pool.c#L13)).
14. **Cache-line layout control.** Worker slots are padded to 64 bytes, and pool fields are grouped by writer with `pad0..pad4` between them ([pool.c:110, 129-203](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/pool.c#L110)).
15. **Persistent pool primitives.** `pause`/`yield` hints, `SwitchToThread`/`sched_yield`, a monotonic nanosecond clock, and per-worker condition variables ([hx_platform.h:105-115](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/hx_platform.h#L105), [pool.c:307-354](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/pool.c#L307)). OpenMP-style fork/join is ruled out at 5–10 µs per region ([hx_pool.h:4-8](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/hx_pool.h#L4)).
16. **Deterministic parallel-for.** Chunks are claimed dynamically through an atomic counter, but each output element is written by exactly one chunk ([hx_pool.h:10-12](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/hx_pool.h#L10), [pool.c:692-705](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/pool.c#L692), [model.c:339-373](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L339)). Mithril should prove write-disjointness statically.
17. **Bounds-checked, overflow-safe parsing of untrusted binaries.** `in_file`, `mul_ok`, strict UTF-8, count caps, region-overlap sort, all-tensor shape checks, and "nothing from the file is used as a size, offset, count or index before it is range-checked" ([modelfile.c:4-9, 62-99, 402-467, 691-809](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/modelfile.c#L4)). Checks must cost nothing in kernels. Three one-past writes into register-allocated SIMD arrays went undetected by every available tool ([T02-kernels-gen-002](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/T02-kernels-gen-002.json)). Static array-bounds proof is therefore a correctness feature as well as a speed feature.
18. **Bit-level float reinterpretation and defined integer semantics.** UBSan once caught a signed-shift UB in the bf16 load ([quant_avx2.c:138](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx2.c#L138), [ci-first-runs.md](https://github.com/pierce-lonergan/hearth/blob/main/governance/reviews/2026-10-05-ci-first-runs.md)).
19. **Conditional compilation by OS and architecture without a textual preprocessor.** `HX_ARCH_X86_64` and the per-OS files ([hx_platform.h:34-48](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/hx_platform.h#L34)).

**P1 — needed for performance parity or a complete port**

20. **No-alias / `restrict` facts** for loop vectorisation ([model.c:586](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L586)), plus a way to add a new ISA kernel (the 94 GMAC/s value pass) that stays bit-identical to the portable loop.
21. **CPU topology queries:** physical cores, affinity, processor groups ([platform_win.c:233-279](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_win.c#L233), [platform_posix.c:178-240](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/platform_posix.c#L178)).

23. **Test seams exported only in test builds:** store read hook, pool rule probes, model sub-batch and parallelism overrides ([store.c:614-622](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/store.c#L614), [pool.c:576-654](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/pool.c#L576), [hx_model.h:118-150](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/hx_model.h#L118)).

### 5. Governance practices

- **Invariants lane.** INVARIANTS.md is carried verbatim. Changing it needs an ADR and a golden update, enforced by `adr.py breaker` ([INVARIANTS.md:3-7](https://github.com/pierce-lonergan/hearth/blob/main/governance/INVARIANTS.md#L3), [governance/README.md:283-324](https://github.com/pierce-lonergan/hearth/blob/main/governance/README.md#L283)).
- **Golden tests.** They are hash-locked by `MANIFEST.sha256`, judged against the base revision's lock, and run in an isolated temporary copy where skips count as failures ([README.md:71-136](https://github.com/pierce-lonergan/hearth/blob/main/governance/README.md#L71), [ADR-0009](https://github.com/pierce-lonergan/hearth/blob/main/governance/decisions/ADR-0009-golden-gate-against-base-revision.md)). They do not cover their own oracle. For Q4/Q8 weights, `hearth.quant` calls the engine's own quantiser, so a change to the quantiser moves the engine and the expected values together ([README.md:438-445](https://github.com/pierce-lonergan/hearth/blob/main/governance/README.md#L438)).
- **Mutation testing.** `mutate.py` makes text-level mutants with eight operator classes and carries a homemade three-valued C preprocessor model so it can skip inactive `#if` branches ([mutate.py:1-80](https://github.com/pierce-lonergan/hearth/blob/main/governance/tools/mutate.py#L1)). Scores run from 65.9% (pool) to 96.4% (model.c lookahead lines) ([H02-platform-pool-gen-001](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/H02-platform-pool-gen-001.json), [R3-forward-gen-002](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/R3-forward-gen-002.json)).
- **Handovers.** Manifests follow a JSON schema with an epistemic ledger (claim, evidence, verdict), procedures and measurements. The `kind` field (measured or simulated) is optional ([handover.schema.json:48-56](https://github.com/pierce-lonergan/hearth/blob/main/governance/schemas/handover.schema.json#L48)).
- **Task DAG.** Tasks own disjoint paths. Contract headers are read-only for everyone except maintainers ([README.md:39-64](https://github.com/pierce-lonergan/hearth/blob/main/governance/README.md#L39)). The DAG has drifted: R3-forward and R3-pool exist as handovers but not as tasks, so strict validation fails ([R3-forward-gen-002](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/R3-forward-gen-002.json)).
- **INV-HONEST.** Every performance claim must state hardware, settings and whether it was measured or simulated ([INVARIANTS.md:20](https://github.com/pierce-lonergan/hearth/blob/main/governance/INVARIANTS.md#L20)). The policy-default study ran timing load-gated, with medians ([policy-default.md:66-75](https://github.com/pierce-lonergan/hearth/blob/main/docs/results/policy-default.md#L66)).
- **Beliefs lane drift.** The engine default became LFU with decay 0.9 ([hx_model.h:71-72](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/hx_model.h#L71)). ADR-0004 still says 0.995 ([ADR-0004:22](https://github.com/pierce-lonergan/hearth/blob/main/governance/decisions/ADR-0004-lfu-default-eviction.md#L22)), and so does the `hx_store.h` comment ([hx_store.h:39](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/hx_store.h#L39)). The tools did not catch it, because they never connect constants to decisions.

## Implications for Mithril

**Language semantics.** [inference throughout]

- **Float arithmetic.** Make `f32` arithmetic strict by default. Offer contraction or reassociation only as explicit, scoped opt-ins, such as `fast { }` blocks marked as output-changing. Give reductions a declared order, such as `sum16` or `seq`, as part of their type, so that vectorisation is legal only when it preserves that order. Integer and exact operations get free reordering. This makes Hearth's split between exact integer work and fixed float work native.
- **Libm.** Make libm calls `extern opaque`: never inlined, folded, vectorised or fused.
- **Kernel portfolios.** Let one function carry several ISA variants and require proof that they are bit-identical. Proof can come from a translation-validation pass, or from a mandatory differential property test against the scalar body that the compiler generates. This is INV-DET-3 as a compiler obligation. Runtime dispatch gets a built-in `cpu.supports(avx512vnni)` that includes the XCR0 checks.
- **Parallel loops.** Add a `par for` whose bodies must write disjoint index sets, checked statically, with a pluggable persistent scheduler. Scheduling then cannot change results by construction (INV-DET-1 and INV-DET-2).
- **Layout.** Provide layout attributes (`packed`, `align(64)`, `line64` padding), little-endian views and static size checks.
- **Parsing.** Provide checked binary-parsing combinators that generate the fuzz corpus from the format spec.
- **I/O.** Model I/O as typed `AlignedBuf<4096>` and `DirectFile`, with positional, concurrent reads. On Windows that means overlapped handles; io_uring and IoRing are later options. Hearth's per-thread blocking reads already reach about 7 GB/s, so Mithril's first job is parity, not a new I/O model.
- **ABI.** Treat the ABI as an artifact. An `export abi` block generates the C header, the ctypes or cffi mirror, and a layout-test file. Structs that cross the ABI carry a size/version field. This removes the drift class that caused the 8-byte overflow.

**Toolchain.** Hearth compiles today with MSVC, GCC and Clang through standard intrinsics. [inference] An LLVM backend with strict FP (no `contract` flags) and target-feature attributes can express everything above. Seed claim B2, "don't target LLVM IR", is not supported by anything Hearth needs. Precedent from Rust: release 1.89 stabilised many AVX-512 intrinsics and target features ([Rust 1.89 release notes](https://blog.rust-lang.org/2025/08/07/Rust-1.89.0/)). The MSVC-equivalent code quality on Windows must be measured, not assumed.

**Governance as language features.**

| Hearth practice | Mithril feature |
|---|---|
| Invariants lane (verbatim, ADR-gated) | `invariant INV-DET-1 { text: "...", enforced_by: test::scheduling_independence }` items whose text hash is in the package lock. Changing one requires a `decision:` reference that the compiler resolves |
| Golden tests, hash-locked and isolated | `sealed test` modules. The toolchain hashes them, runs them hermetically, and treats skips as failures. Changing one needs a signed maintainer attestation, verified against the base revision's lock |
| Golden oracle independence | Oracle provenance: a sealed test declares which modules are its oracle. The compiler refuses a change touching both the oracle and the code under test (catches the quantiser hole) |
| Mutation testing | AST- and type-aware mutation built into the compiler, incremental on the diff, with no preprocessor model, plus SMT/e-graph detection of equivalent mutants |
| INV-DET-1/2/3 | `deterministic` effect: no clock, thread-id or address reads in value-producing code. A batch-invariance property derived automatically. Equality of ISA variants as above |
| INV-HONEST | Typed `Measured<T>{hw, load, settings, baseline}` and `Simulated<T>`. The doc and benchmark tools refuse untyped numbers. `kind` is mandatory |
| INV-LOSSLESS-DEFAULT | `lossy` effect on configuration fields. The compiler rejects a lossy default |
| ADR beliefs lane | `@decision(ADR-0004)` annotations on constants and defaults. Drift warnings when an annotated value differs from its decision record |
| Task DAG with disjoint ownership | Module ownership in the manifest. Sealed contract interfaces (the `hx_*.h` equivalents). Builds that fail when a change set touches unowned modules |
| Handovers | The toolchain emits a session manifest: what was built and tested, with exact commands and typed measurements, ready to validate |
| Friction | The test runner keeps masked error signatures and blocks a fourth identical retry without a root-cause note |

## Implications for Hearth

- **Cross-binary oracle.** Add a corpus of SHA-256 logits hashes now: every `make_tiny` architecture × {F32, Q4} × ISA, plus `big_q4`, plus real Qwen3 decode steps. Keep it beside the golden suite, and record the CRT/libm identity in its conditions. This is useful to Hearth even without Mithril: it catches libm or compiler upgrades that change output.
- **ABI hygiene.** Add a `struct_size` field to `hearth_options` and `hearth_stats` (a maintainer contract change). The uncommitted R3 work grows both structs ([hearth.h:85-88, 122-127](https://github.com/pierce-lonergan/hearth/blob/main/engine/include/hearth.h#L85)).
- **Port base.** Fix the 0.995 versus 0.9 drift with a superseding ADR. Add R3 tasks to tasks.json. Tag the base commit for the port.
- **Value pass.** Land the 94 GMAC/s AVX-512 value pass as an `hx_kernels` entry. It is the largest known codegen gap and gives Mithril a concrete target.
- **INV-DEP.** Decide whether "C11 + OS APIs only" can be superseded by "Mithril + OS APIs". Without that, the port cannot be merged under Hearth's own rules.

## Where the seed discussion is right or wrong

- **B1 (C hides throughput through aliasing and sequential semantics).** *Partly right and minor for decode.* Fully cached decode reaches about 52 GB/s against about 60–78 GB/s achievable [inference, §3]. The aliasing-sensitive value pass shows a 5× codegen gap (18 against 94 GMAC/s), but only in attention.
- **B2 (avoid LLVM IR).** *Unsupported.* Every Hearth need is expressible in today's C toolchains.
- **B4 (`line64` alignment).** *Right.* The pool pads every hot field to a 64-byte line ([pool.c:129-203](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/pool.c#L129)). *Streaming stores: no evidence.* Hearth uses no non-temporal stores, and slabs arrive by DMA.
- **B5 (no pointers, affine DAGs).** *Right for kernels, wrong for the runtime.* The store indexes slots dynamically (`slot_of`), counts references, and takes offsets from validated file data.
- **B6 ("no scalar loops", guaranteed vectorisation).** *Wrong as stated.* The scalar body is the specification ([quant.c:1-8](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L1)). Vectorisation must preserve its order, and masks are needed only for tails.
- **B8/B9 (superoptimiser plus SMT equivalence).** *Right only where math is exact.* Integer block sums can be searched freely. Float order is fixed, so any equivalence check must be bit-exact under IEEE.
- **B10 (dual P/E-core paths).** *Not applicable* to this Zen 5 desktop [inference]. Any per-core variant would also have to be bit-identical.
- **B11 (rigorous harness, pinned and quiet machines).** *Right.* It matches INV-HONEST and Hearth's load-gated medians. Hearth still lacks quiet-machine numbers ([H02-platform-pool-gen-003](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/H02-platform-pool-gen-003.json)).
- **C1/C2 (roofline caps the gains).** *Right.* For example, DDR5-6000 dual channel is 96 GB/s theoretical [inference: 2 × 8 B × 6000 MT/s], with about 78 GB/s measured read per Hearth's profile.
- **C3 ("60–90% of compute wasted").** *Wrong for Hearth decode* (about 15–35% below achievable bandwidth [inference]). Plausible only for prefill and attention compute, where roughly 3 of about 20 TOPS are used [inference].
- **C4 (whole-layer fusion with no intermediate writes).** *Must be constrained.* Per-(token, rank) expert buffers exist so that completion order cannot change the sum ([model.c:937-957](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/model.c#L937)). Hearth already fuses SwiGLU with quantisation.
- **C5 (sparsity via VGATHER).** *Contradicted by measurement.* Packing scales in general-purpose registers was faster than `vpgatherdd` in both kernels ([quant_avx2.c:63-64](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx2.c#L63), [quant_avx512.c:243-244](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant_avx512.c#L243)).
- **C6 (low-bit types lowering to VNNI).** *Right in direction, and Hearth already does it* (`vpdpbusd` with a +8/+128 bias). Nibble unpacking remains necessary.
- **C7 (deep software prefetch, many iterations ahead).** *Not supported at Hearth's granularity.* Deeper lookahead raised hit rate but slowed decode, adding 7–17% NVMe bytes per token per extra depth ([policy-default.md:12-14](https://github.com/pierce-lonergan/hearth/blob/main/docs/results/policy-default.md#L12)). Simulated, 72.8% of one-layer prefetches arrive late ([qwen3-routing-and-cache-policy.md:41-42](https://github.com/pierce-lonergan/hearth/blob/main/docs/results/qwen3-routing-and-cache-policy.md#L41)).
- **D1–D7 (claimed speed-ups).** *Unsourced and implausible for memory-bound decode.* The IPC and 3–5× CPU-only claims (D3, D6) conflict with §3. D4 (hiding 70–85% of transfer latency) is contradicted by Hearth's lookahead results. Kimi-K2 decode is NVMe-bound (about 11 GB per cold token) [inference].
- **G1 (SPDK) / H7 (user-space DMA).** *Low value here.* Hearth's demand reads reach 7.16 GB/s, close to the 990 PRO's 7.45 GB/s spec cited in Hearth's profile ([hardware.py:81](https://github.com/pierce-lonergan/hearth/blob/main/python/hearth/sim/hardware.py#L81)). SPDK-style user-space NVMe is not an option on the Windows-first target [inference].
- **H2 (drop-in C-FFI / Python binding).** *Right and essential.* The ABI is the acceptance boundary.
- **H5 (machine-actionable diagnostics).** *Right.* Hearth's friction signatures and handovers are precursors.
- **I5/I7 (hot-patching, self-modifying code).** *Unnecessary for Hearth.* Dispatch is a function table chosen once ([quant.c:479-501](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/quant.c#L479)). JIT adds W^X and determinism risk. The "single CPU cycle" CMPXCHG claim is unverified.

## Staged port plan

The acceptance oracle at every stage has three parts: (a) the unchanged C test suites, linked against the mixed build; (b) the golden suite run through `check_golden.py --run`; (c) the cross-binary hash corpus, which must be byte-identical to the C build on the same OS, CRT and ISA. Performance gates are interleaved and load-gated A/B medians against the C build on the same machine (INV-HONEST).

0. **Freeze and instrument.** Tag the port base. Build `hearth-c-ref`. Generate the hash corpus: logits, routes, `hearth_quantize` bytes for every dtype, and `hearth_matmul` outputs across ISA, T, row splits and NaN/inf inputs. Mithril emits the internal `hx_*` C symbols so that its modules can replace C objects one at a time in `hearth_core` ([CMakeLists.txt:48](https://github.com/pierce-lonergan/hearth/blob/main/CMakeLists.txt#L48)).
1. **Leaf numerics.** Half conversions, `quant.c` formats, quantisers, scalar kernels and canonical helpers; then AVX2; then AVX-512 with masks and VNNI. Gate: test_quant (117,681 checks per [T02-kernels-gen-002](https://github.com/pierce-lonergan/hearth/blob/main/governance/handovers/T02-kernels-gen-002.json)), golden kernel identity, a byte diff of quantiser output against C (this covers the oracle hole), and ≥ 69.6 GB/s single-thread Q4.
2. **Parser.** `modelfile.c`. Gate: test_modelfile fuzz cases, the golden malformed-file test, and identical accept/reject decisions and parsed configs on a generated corpus.
3. **Pool.** Gate: test_pool and dispatch latency within noise of C (about 0.75 µs at 16 threads).
4. **Platform I/O and store.** Gate: test_platform, test_store, golden scheduling independence, and ≥ 7 GB/s peak demand reads.
5. **Forward pass.** Gate: the full golden suite, the hash corpus, real-model decode hashes (512 steps) and tok/s parity at 2, 4 and 8 GiB caches.
6. **API.** Mithril exports `hearth.h`. Python runs unchanged. The ABI-mirror test passes. Retire the C core, but keep `hearth-c-ref` permanently as a differential oracle.

## Risks

- **Libm identity.** Bit equality with C requires the same CRT `expf`, `sinf` and `cosf`. A Mithril-native math library breaks it. Libm upgrades can change outputs ([CORE-MATH](https://core-math.gitlabpages.inria.fr/)).
- **False equivalence.** The golden suite alone cannot detect a consistent but different float order. The quantiser shares its oracle with the code under test.
- **ABI.** Structs grow without a size field. Drift has already caused one memory overwrite.
- **Windows codegen parity.** Matching MSVC `/O2` kernel throughput and the heavily tuned pool heuristics (WSL2 and Windows scheduler cases in [pool.c:21-101](https://github.com/pierce-lonergan/hearth/blob/main/engine/src/pool.c#L21)) is a performance risk.
- **Constitutional conflict.** INV-DEP and ADR-0001 must be superseded, which trips the circuit breaker.
- **Moving target.** There are uncommitted R3 changes, H02 is still in review, and macOS arm64 has no SIMD kernels and open CI failures.
- **Bounds-check cost.** Any bounds checks that cannot be proven statically in kernels cost throughput directly.

## Open questions

1. Is bit-identity with the C binary required, or only passing the golden suite? The two differ if Mithril ships its own libm.
2. Should NUMERICS adopt correctly rounded `expf`, `sinf` and `cosf` to make determinism hold across machines? That would need an ADR and golden changes.
3. Will Hearth's maintainers supersede INV-DEP for Mithril?
4. Should Mithril use an LLVM backend with strict FP, or its own backend? Hearth gives no evidence that LLVM blocks anything.
5. Which commit is the port base, given the uncommitted R3 work?
