# 07 — The Hearth port

Hearth is Mithril's acid test. This document says how Hearth's C11 engine moves to Mithril one
module at a time without changing a single output bit. The port is a strangler fig behind Hearth's
internal `hx_*.h` seams. Mithril emits C11 defining the same `hx_*` symbols, and that C is checked
in and regenerated byte for byte in CI (DR-026). Stages run S0 freeze and instrument → S1 quant
kernels → S2 modelfile → S3 pool → S4 store logic over the existing C platform functions → S5
forward pass → S6a API → S6b platform layer, last (DR-020). Each stage must pass:

- the unchanged C tests;
- the golden suite through `check_golden.py --run`;
- a new cross-binary hash corpus;
- the quantiser byte diff;
- an interleaved, load-gated non-inferiority A/B against `hearth-c-ref` (DR-018).

ADR-0010, "specified transcendentals", must land in C Hearth before the corpus is built (DR-014).
Exact kernels need `validated` evidence; other logits-path code may be `tested` plus the corpus,
labelled as such (DR-021). The document also covers:

- the decisions only Hearth's maintainers can make;
- the comprehension precondition for each stage, and rebase windows for upstream changes;
- how generated C is reviewed;
- the defects the research found;
- what Kimi-K3 and MXFP4 imply;
- how meanings relate to the numpy reference;
- what Hearth keeps if Mithril stops.

## 1. What the port is, and what it is not

**Shape.** Hearth's layering is strict: `api → model → {store, pool, quant} → modelfile →
platform` ([R11]; ADR-0001, ADR-0007). All C sources are compiled into one CMake OBJECT library,
`hearth_core`, which links into the `hearth` DLL, the benchmark tool and every C test
(`CMakeLists.txt:48`). A Mithril module replaces a C file's entry in that library. It defines the
same symbols, declared in the same hand-written `hx_*.h` headers. The C compiler therefore
type-checks every generated definition against the seam declaration for free.

```
 engine/mith/*.mith --mithc (pinned)--> engine/gen/*.c  (checked in; CI regenerates byte for byte)
                                           | defines the same hx_* symbols as the C it replaces
                                           v
 +------------------------- hearth_core (CMake OBJECT library) -------------------------+
 | api.c [S6a]  model.c [S5]  store.c [S4]  pool.c [S3]  modelfile.c [S2]  quant*.c [S1] |
 |              platform_win.c / platform_posix.c / platform_common.inc  [S6b, last]    |
 +---------------------------------------------------------------------------------------+
        | hearth.dll / libhearth.so                     hearth-c-ref@<tag> (frozen C build)
        v                                                         |
 ctypes mirror -> Python toolkit -> golden suite        cross-binary hash corpus (SHA-256)
        +---------------- interleaved, load-gated A/B (same session) ----------+
```

The directory names `engine/mith/` and `engine/gen/` are a proposal.

**What "zero output change" means.** INV-DET-1 is scoped "for a fixed binary and ISA"
(`governance/INVARIANTS.md`). Zero output change therefore has two parts [R11]:

1. bit-identical logits, routes and quantiser bytes to the C build on the same OS, CRT and ISA
   (after ADR-0010, on every supported OS: §3);
2. every golden test and C test passes.

**What the port is not.** It is not a speed project.

- The lossless decode ceiling for Qwen3-30B-A3B is about 34 tok/s at 77 GB/s of measured DRAM
  bandwidth [inference].
- Hearth measures 19–22 tok/s (noisy), so honest CPU headroom is about 1.5x [R08].
- The largest lossless lever, the GPU tier, is outside the port (§9.2). Its simulated 3.6–4.8x
  [G03] assumes backbone and experts in VRAM, attention included, which DR-022's first tier
  excludes.

The port is judged on parity, assurance and agent maintainability: benefit claims B1–B3 in
[../ROADMAP.md](../ROADMAP.md).

**Scope by module** (counted, working tree; [R11]):

| Module | C lines | Seam | Stage | C tests that gate it (lines) |
|---|---:|---|---|---|
| `quant.c`, `quant_avx2.c`, `quant_avx512.c` | 682 + 351 + 375 | `hx_quant.h` (87) | S1 | `test_quant` (1,614) |
| `modelfile.c` | 922 | `hx_modelfile.h` (93) | S2 | `test_modelfile` (1,763) |
| `pool.c` | 732 | `hx_pool.h` (62) | S3 | `test_pool` (2,478) |

| `platform_win.c`, `platform_posix.c`, `platform_common.inc` | 693 + 511 + 370 | `hx_platform.h` (184) | S6b | `test_platform` (1,744) |

The engine totals 9,068 lines of C11 (8,827 in `engine/src` and `engine/include`, plus the
241-line benchmark tool). Its C tests total 14,859 lines (counted [R11]).

## 2. The acceptance oracle used at every stage

Each stage is accepted only when all five checks below pass. Each check covers a hole the others
leave.

### 2.1 The C test suites, unchanged

The six C test programs link `hearth_core` directly and run against the mixed build with no edits.
`test_quant` alone performs 117,681 checks (counted; handover T02-kernels-gen-002). Mutation scores
range from 65.9% for the pool to 96.4% for the model.c lookahead lines (measured [R11]), so S3 adds
gates (§4).

### 2.2 The golden suite through `check_golden.py --run`

`--run` verifies the hash lock against the base revision (ADR-0009, still Proposed, but implemented
in the tooling). It then runs the suite in an
isolated copy, where skips count as failures. The suite has eight tests over five architectures ×
{F32, Q4}, plus `big_q4` (`tests/golden/test_golden_invariants.py:22-42`). It checks:

- relational equalities within one build: scheduling independence, batch = sequential, ISA
  identity;
- tolerance against the numpy reference: 1e-3·max(1, max|logit|) on F32, 2e-2 on Q4;
- exact routing equality;
- clean failure on malformed files.

**It pins no absolute logits** [G04 F8], so a port with a different but self-consistent float order
would pass it [R11].

### 2.3 The cross-binary hash corpus

This is the new oracle that makes "zero output change" checkable. Hearth already used the technique
once: SHA-1 of the logits at all 512 steps of a real-weight decode, reproduced across 48 policy
configurations, 42 depth configurations and the previous commit's DLL (measured;
`docs/results/policy-default.md`). The corpus generalises that.

| Part | Inputs | What is hashed (SHA-256) | Where it runs |
|---|---|---|---|
| Synthetic engine | `make_tiny` containers (`python/hearth/synth.py:203`) for the five architectures × {F32, Q4} with fixed seeds, plus `big_q4`; ISA ∈ {scalar, AVX2, AVX-512}; one token at a time and batched; at least two thread counts and cache budgets | logits per step; routes (top-k ids per token per layer) | CI, every OS |
| Kernels | `hearth_matmul` per dtype × ISA × the T values and row splits `test_quant` exercises; inputs including NaN, ±inf, ±0 and subnormals | output bytes | CI |
| Quantiser | `hearth_quantize` per dtype on seeded inputs plus edge values | output bytes, kept whole for the byte diff (§2.4) | CI |
| Real model | Qwen3-30B-A3B Q4 from the data directory; 512 decode steps at 2, 4 and 8 GiB caches; 512- and 2,048-token prefills | logits per step; greedy tokens | owner's 9950X only (INV-DATA keeps models out of CI) |
| Conditions | — | commit; compiler and toolset; flags; CRT/libm identity (`ucrtbase.dll` or glibc version); `_get_FMA3_enable()` state; CPU flags; canon version | stored with every entry |

**Ownership.** The synthetic, kernel and quantiser hash lists live under `tests/golden/corpus/`,
locked by the existing `MANIFEST.sha256` and recomputed by a golden test. The existing gate
machinery then covers corpus changes with no new governance code. The real-model list is locked the
same way, but checked by a maintainer-run script, because CI cannot hold the model. Each run is a
signed ledger record with a hardware fingerprint ([03-trust.md](03-trust.md)).

**Regeneration.** The corpus changes only through:

- an ADR-approved output change under INV-LOSSLESS-DEFAULT;
- a canon migration ([03-trust.md](03-trust.md));
- added entries.

It is never regenerated to make a port step pass. A re-baseline is an AUTHORITY operation signed by
the Owner, and it invalidates every ledger claim keyed on the old corpus hash.

**OS keying.** Before ADR-0010 the corpus is keyed by CRT identity. After ADR-0010 and INV-DET-4
(§3), one synthetic hash set should cover every CI OS [inference, G04].

### 2.4 The quantiser byte diff

For Q4 and Q8 weights, `hearth.quant` calls the engine's own quantiser. A change to the quantiser
therefore moves the engine and the golden suite's expected values together. That is an oracle hole
[R11]. The fix is to compare every dtype's `hearth_quantize` output byte for byte with
`hearth-c-ref`, at S1 and at every later stage. Add the oracle-provenance rule [P3 §3.8]: a change
set may not touch both an oracle (here the quantiser) and the code it judges. Mithril's store
enforces that rule by role capability ([03-trust.md](03-trust.md)).

### 2.5 Interleaved, load-gated non-inferiority A/B

DR-018 sets the gate:

- non-inferiority with margin δ = 3%, judged by an anytime-valid e-value;
- both builds from the same commit and flags, interleaved in randomised blocks in one session,
  load-gated on a declared quiet-machine profile;
- superiority claims need e ≥ 20;
- absolute figures are context only, such as 69.6 GB/s single-thread AVX-512 Q4, measured
  L2-resident on a busy machine [R11].

Hearth's own load-gated, interleaved, median-reporting protocol (`docs/results/policy-default.md`)
is the starting point. Blocking, stationarity checks, machine controls and the pass threshold are
specified in [06-forge.md](06-forge.md).

### 2.6 What evidence each gate produces (DR-021)

| Code | Claim | Admissible grade for release | Evidence |
|---|---|---|---|
| Exact kernels (matvec, matmul, act-quant, `sum16`/`dot16`, canonical transcendentals) | `refines(variant, meaning)` | `validated` | T1/T2 on the object code via the object audit (B1.5, DR-008): effective `validated(partition)` from table and rewrite-list premises, code floor `tested` printed beside it ([03-trust.md](03-trust.md) §3.2). A variant that fails to lift or match drops to `tested` and is **not dispatched** in release profiles |
| Non-kernel logits-path code (attention orchestration, norms, router, RoPE driver, MoE combine) | `refines(module, hearth_c_ref::module)` | `tested`, labelled | C tests + golden + hash corpus + `mithi` differential |
| Weight quantiser | `refines` | `tested`, labelled | full byte diff over the corpus |
| Parser | `safe` and total (INV-FMT/SAFE) | `tested` (fuzz, `mithi` differential, golden malformed-file); `proof` only for the bounds obligations T2 discharges, at source level ([../ROADMAP.md](../ROADMAP.md) §7 B1) | the derived parser has no `unsafe`; plus a differential accept/reject corpus. It is generated by an untrusted `mithc`, checked by a front end graded `tested` and compiled by a trusted C compiler, so no stronger claim is delivered |
| Store | `deterministic` across the store boundary | the grade of the cited evidence | `deterministic(by: golden::scheduling_independence)`; the store-core theorem O1–O5 graded `validated` until mechanised (DR-010) |
| Every stage | `perf` | measured(hw) | §2.5 |

The rule that `refines` for an exact kernel *slot* admits proof or validated, never tested
([03-trust.md](03-trust.md) §2.2), covers swappable or searchable realisations. model.c's
orchestration is not a slot, and 03 §2.2 gives non-kernel logits-path code its own row, so
DR-021's labelled `tested` applies:

```mith
/// Claims for Stage S5, owned by the Author role and hash-locked.
spec s5_forward_claims for forward_token {
    claim refines(q4_matvec_avx512, q4_matvec) requires validated;       // exact kernel slot
    claim refines(forward_token, hearth_c_ref::forward_token) requires tested;
        // not a slot: C tests + golden + hash corpus; every report prints "tested"
    claim perf(forward_token) requires measured
        noninferior(to: hearth_c_ref::forward_token, margin: 3%);
}
```

## 3. ADR-0010 before the corpus

**The problem.** NUMERICS.md says `expf`, `sinf`, `cosf` and `sqrtf` "come from the platform libm",
and §4 defines SiLU, sigmoid, softmax and RoPE with them (`docs/NUMERICS.md:13, 64-77`). `cosf` and
`sinf` go through volatile function pointers, because Apple clang's `sincos` fusion broke macOS CI
(`quant.c:653-666`, `model.c:219-235`). "The platform libm" is not one function (measured on this
machine [G04]):

- UCRT picks an FMA3 or non-FMA3 path at startup. Over all 2^32 inputs the two disagree on 1
  `expf`, 44,232 `sinf` and 18,018 `cosf` results.
- UCRT `expf` misrounds 23,276 inputs, and `sinf`/`cosf` about 2.87 million each.

Parity therefore depends on CPU features and the Windows build, and a glibc update could change
Linux logits with no change to Hearth.

**The decision ADR-0010 should record** [G04; P5 §9.2; P3 §9]:

1. Replace "platform libm" with named, specified functions:
   - `sinf` and `cosf` become correctly rounded scalar functions (`cr`). RoPE makes about 128 calls
     per token for Qwen3-30B-A3B [inference from head_dim 128], so the cost is negligible.
   - `expf` becomes either a correctly rounded scalar function (about 1% of decode or prefill
     time [inference]) or a Hearth-authored `canon.v1` algorithm. The latter is a fixed op-DAG of
     IEEE basic operations with no FMA, written in C11 for scalar, AVX2 and AVX-512 in canonical
     order. A prototype was bit-identical across all three ISAs over all 2^32 inputs. It was
     99.19% correctly rounded with a maximum error of 1 ulp, and ran at 0.204 ns/element on
     AVX-512 against 1.12 ns for scalar UCRT `expf` (measured [G04]).
   - `sqrtf` needs no change: IEEE 754 makes it correctly rounded. It must stay a true `sqrtf`,
     never an `rsqrt` approximation.
2. Record the measured output-change rate under INV-LOSSLESS-DEFAULT. Nearly every token's logits
   change once, and so do 11–13% of RoPE positions [G04 F3].
3. Update the bit-exact C references in `test_model.c` and `test_quant.c`. The golden suite needs
   **no re-lock**, because it is relational and tolerance-based [G04 F8].
4. Propose INV-DET-4, cross-OS hash equality, as a separate invariant ADR.
5. Extend NUMERICS §3's canonical-NaN rule (`0x7fc00000`) from matvec outputs to the §4
   elementwise outputs (softmax, RMSNorm, SiLU/SwiGLU, sigmoid, RoPE), which store raw payloads
   today (`quant.c:626-679`). Mithril kernels canonicalise at every sink ([02-compute.md](02-compute.md)
   §2), so without this the port would differ from C on NaN inputs [inference]. It changes
   outputs only where a NaN already appears.

**Why before the corpus.** Built afterwards, the corpus is created once, on the final semantics.
Built before, it needs a re-baseline: an AUTHORITY operation with ledger invalidation and a second
real-model run. Still open for maintainers [G04 open questions 1–2]:

- Does CORE-MATH build under MSVC?
- Does vendored MIT source count as a "third-party library" under INV-DEP? Hearth-authored
  functions avoid this question.

Correctly rounded binary32 functions are verified exhaustively. The G04 probe covered 2^32 inputs,
three functions and two CRT paths in about 22 s on 32 threads (measured). That evidence is
`validated`.

**In Mithril.** Exact code must name the namespace (DR-014). Hearth's ADR-0010 choices become
call sites:

```mith
/// NUMERICS §4 softmax after ADR-0010 (hx_softmax, quant.c:634). Exact code names its
/// transcendental; a bare platform `expf` is rejected in exact code.
kernel fn softmax(x: &mut [f32])
    requires x.len() > 0
{
    let mut m: f32 = x[0];
    for i in 1..x.len() {
        if x[i] > m { m = x[i]; }              // the same comparison as hx_softmax
    }
    for i in 0..x.len() {
        x[i] = canon_v1::expf(x[i] - m);       // fixed op-DAG: bit-identical on every ISA
    }
    let s = canon::sum16(x);                   // 16 lanes, then the 8, 4, 2, 1 tree
    for i in 0..x.len() {
        x[i] = canon::nan(x[i] / s);           // kernel sink: NaN stored as 0x7fc00000
    }
}
```

The last loop is the kernel's sink, so it canonicalises NaN as every kernel output must
([02-compute.md](02-compute.md) §2). `hx_softmax` does not do this today: NUMERICS §3 states the
canonical-NaN rule only for matvec outputs, and x86's default NaN is `0xffc00000`. Item 5 of the
ADR-0010 decision above closes that gap in C before the corpus is built, so the meaning and
`hearth-c-ref` agree on NaN inputs too.

RoPE calls `cr::sinf` and `cr::cosf`. `canon_v1::expf` also carries over to a future PTX backend
by construction, which matters for DR-022 ([02-compute.md](02-compute.md)).

**If maintainers decline.** The port then uses a parity shim: an FFI call to the CRT carrying the
`nondet(platform)` effect, allowed only on Hearth's legacy path. The corpus records the
`ucrtbase.dll`/glibc versions and the FMA3 state. INV-DET-1 is reworded to "fixed binary, CRT/libm
build and CPU feature set", and one re-baseline is planned for whenever the specification changes
[G04 §Implications for Hearth, 6].

Every stage is recorded in the ledger in the same shape:

```text
stage S1 {                                        // a ledger fact, shown as text
    replaces:     [quant.c, quant_avx2.c, quant_avx512.c]
    base:         hearth-c-ref@port-base-1        // git tag + corpus hash
    precondition: harness(T-Q4, T-ACTQ) clears its pre-registered bar   // section 5; 05 §13
    gates:        [ctest(test_quant), golden(--run), corpus(all), quantiser_bytes(all dtypes),
                   refines(validated) for each dispatched variant, perf(noninferior 3%)]
    on_fail:      module stays C behind hx_quant.h; tombstone { scope, class, revisit_when }
}
```

**Exit rule.** A module that misses its gate within its time box stays C behind its seam. That is
recorded as a scoped tombstone with a resurrection trigger ([06-forge.md](06-forge.md)). If more
than two modules stay C, the port is re-planned. A hash-corpus mismatch traced to language
semantics is a kill criterion, not a tuning item [P1 M5; P5 M5; ROADMAP].

### S0 — Freeze and instrument (M0, C-side)

Steps, in this order:

1. **Commit R3 and repair the DAG.** 17 files and 3 handovers are uncommitted, and the R3 tasks are
   missing from `tasks.json`, so strict validation fails [R11].
2. **Constitutional ADRs** (§9). Add `struct_size` with R3, which already grows `hearth_options`
   and `hearth_stats` (`git diff engine/include/hearth.h`).
3. **Land ADR-0010 in C.**
4. **Tag and build** `hearth-c-ref@port-base-1` with the release flags (`CMakeLists.txt:37-60`).
5. **Generate the corpus** (§2.3) twice and compare.
6. **Byproducts on the frozen objects:**
   - the X0 instruction census and the object audit of today's C kernels (DR-008,
     [04-toolchain.md](04-toolchain.md));
   - Hearth's past rejections (lookahead depth 4, slow-decay LFU) imported as tombstones, with a
     replay test of their triggers ([06-forge.md](06-forge.md)).

**Gate:** the corpus is reproducible twice, ADR-0010 is decided before it is locked, and the Owner
signs it.

### S1 — Quant kernels (v0, M1–M2)

**Scope.** Half conversions, formats as `format` types, quantisers, activation quantisation,
scalar kernels, canonical helpers (including ADR-0010's functions), ISA dispatch, and the AVX2 and
AVX-512 kernels.

**Route.** One meaning plus per-ISA schedules ([02-compute.md](02-compute.md)). If X3 fails, the
kernels are written as explicit-SIMD `.mith` transliterations (`mithc lift`), which T1 checks the
same way [P5 §10.1].

**Gates.**

- `test_quant`, golden ISA and batch identity, the corpus, and the quantiser byte diff.
- `validated` evidence through the object audit for every dispatched variant.
- Non-inferiority for single-thread Q4/Q8 matvec per ISA, and for cached decode (21.88 tok/s
  measured [R11]).

Three one-past writes into SIMD arrays escaped every tool (T02 [R11]). DR-011 turns that class into
compile errors.

### S2 — Modelfile (v0, M3)

**Scope.** The parser becomes `format` descriptions that derive a total parser and writer
(`modelfile.c:4-16`). "Nothing from the file is used before it is range-checked" becomes a property
of the derived parser's types, checked at source level and graded as §2.6 says. Dense-load I/O still
calls the C platform functions.

**Gates.** `test_modelfile` fuzz cases and the golden malformed-file test; identical accept/reject
decisions and configs on a generated corpus (≥ 10^6 files [inference, P5]); zero `unsafe`; totality
and safety `tested` by fuzzing, the `mithi` differential and the golden malformed-file test, with
`proof` only for the bounds obligations T2 discharges ([../ROADMAP.md](../ROADMAP.md) §7 B1); open
time non-inferior.

**Kill.** If parsing is more than 1.3x slower than C, or the diff is non-zero after three weeks,
keep the C parser [P5 M3].

### S3 — Pool (v0, M4)

**Scope.** The persistent pool, including its seq_cst sleep handshake (`pool.c:4-101` [R11]).
`par for` with statically checked write-disjointness replaces `hx_pool_for`'s convention.

**Gates.**

- `test_pool`.
- Dispatch round trips non-inferior at 16 threads (about 0.75 µs) and 32 threads (about 7.5 µs),
  measured under load [R11], including the WSL2 and crowded-pool cases.
- The loom-style permutation scheduler.
- ThreadSanitizer.

The last two are required because the pool's C tests have the lowest mutation score.
Write-disjointness is graded `tested` until the Core is mechanised (DR-010).

### S4 — Store logic over the existing C platform functions (v0, M4)

**Scope.** `store.c` becomes `Mutex<StoreState>` over integer-indexed metadata. Slab bytes move as
a linear `SlabBuf`, frozen into `Frozen<SlabBuf>` and reclaimed when unique [G05]. Eviction and
prefetch become `timing_only` hint ports under the store-core certificate O1–O5
([02-compute.md](02-compute.md)). The store calls today's C platform functions through the
`std_platform` interface, which keeps store risk apart from Unsafe risk [P3 §9; G05].

**Preconditions.** The heat decay is decided. INV-DET-1's mirror clause is qualified, or per-slab
hashes exist: O4 cannot be claimed while `check_mirror` samples. The integer-handle style is kept.

**Gates.**

- `test_store`, `test_platform`, golden scheduling independence.
- Non-inferior demand reads (7.16 GB/s measured [R11]) and 2 GiB-cache decode (13.02 tok/s,
  401 MB/token measured [R11]).
- The chaos suite kills 100% of seeded core mutants.
- ≥ 100 type-checked generated policies give bit-identical logits in one golden run [target; P1, P4].
- Zero user `unsafe` outside `std_platform`; audited `unsafe` ≤ 1,500 lines across OSes (the M4
  gate, [../ROADMAP.md](../ROADMAP.md) §5).

**Kill (memory model, S3 and S4 together; [../ROADMAP.md](../ROADMAP.md) §5 M4).** User `unsafe` in
more than 2 places, or dispatch above C + 10% that cannot be closed, reopens the memory model. One or
two places is amber: an audited primitive admitted by ADR [P5].

The `hx_store_heat` race (§10) cannot be written; the replacement copies and declares its timing
dependence:

```mith
/// Copy the heat counters out under the lock. The C version (store.c:612) returns a pointer
/// into lock-protected state; a reference cannot escape `with_lock`, so that cannot be written.
fn heat_into(store: &Store, out: &mut [f32]) uses { nondet }
    requires out.len() == store.n_heat()
{
    store.state.with_lock(|s| {
        for k in 0..out.len() { out[k] = s.count_f[k]; }
    });
}
```

`acquire` instead crosses `deterministic(by: golden::scheduling_independence)` (canonical snippet),
and value-level claims on its outputs inherit that evidence's grade. Input-universal claims, such as
a downstream kernel's `refines`, are not capped by it ([01-language.md](01-language.md) §7.2).

### S5 — Forward pass (v0, M5)

**Scope.** `model.c`: GQA and absorbed-form MLA attention, routers, shared experts, batched
evaluation, lookahead prefetch, trace and replay, rollback of failed calls (`model.c:1321-1396`).

**Gates.**

- The full golden suite, the corpus, and 512-step real-model decode hashes.
- Non-inferior tok/s (δ = 3%) on the confirmatory set: cached, 2 GiB and 2,048-token prefill; the
  4/8 GiB and 512-token prefill configurations are screened and escalated per ROADMAP §1 rule 4
  (prefill baselines 345–433 and 226 tok/s measured [R11]).
- An overhead check for traps and hidden copies on hot paths (DR-027,
  [04-toolchain.md](04-toolchain.md)).

**Opportunity, not gate:** an exact F1 schedule for the attention value pass (register-blocked,
each output's accumulation order unchanged). Hearth's portable loop already declares every pointer
`restrict` and runs at 18.0 GMAC/s (SSE2 under MSVC); a bit-identical AVX-512 C prototype, with
8 heads × 32 dims in 16 zmm accumulators and multiply-then-add, reaches 94 (measured [R11];
handover H03-forward-gen-001). The gap is therefore closable in C11 by a schedule: a
schedule-space candidate for the Forge ([06-forge.md](06-forge.md)), not a trigger for backend B3,
the direct x86 emitter, because DR-009 needs a gap attributable to codegen. If it moves tok/s by
≥ 5% on a named configuration (2,048-token prefill is the likeliest), it can serve as the certified
gain in benefit claim B3 ([../ROADMAP.md](../ROADMAP.md) §7) [inference]. `restrict` emission from
alias facts (DR-027) only keeps parity with the hand-annotated loop.

### S6a — API (v0, M5)

**Scope.** `api.c`: validation that never crashes, environment overrides, defaults and the log lock

**Gates.**

- ABI identity with `hearth.h` (19 functions, 3 structs, `struct_size` since S0), checked by a

## 5. The comprehension precondition

**The rule.** Before stage *k* starts, each harness task family listed for it below must clear its
pre-registered verified-pass@1 bar with the Tier 0+1 card and the project card [P1 §9]. This ties
the AI-first claim to each port step: Mithril code nobody can maintain should not replace C code
agents can maintain. The port also becomes the harness's largest external validation set.

The stage-to-family table is owned by [05-agent-protocol.md](05-agent-protocol.md) §13 and
repeated in [../ROADMAP.md](../ROADMAP.md) §5. It is copied here; if the copies differ, 05 wins.

| Stage | Task families (05 §13) |
|---|---|
| S1 | T-Q4 (bit-exact Q4 dot and matvec), T-ACTQ (activation quantisation) |
| S2 | T-FMT (bounded container parser) |

**Proposals for 05 §13, not gates until 05 adopts them** [inference]:

- T-NORM at S1 as well, because `hx_rmsnorm` and `hx_softmax` live in `quant.c` (§3) and port with

## 6. Upstream changes during the port: rebase windows

Hearth will keep moving: R3 is uncommitted, macOS CI is open, and Kimi-K3 is on the roadmap. The
proposals stop at "freeze and tag", plus P5's one-line "rebase window at each stage boundary". The
judges asked for the actual policy.

**Module states:**

| State | Meaning | How upstream changes are handled |
|---|---|---|
| C-live | not yet ported | normal upstream development |
| porting | its stage is in progress | **port-lock**: non-fix changes wait for the next window; fixes are made in C and mirrored into `.mith` within the stage |
| Mithril-live | stage gate passed; generated C on by default | edits go to `.mith`; the hand-written C is frozen as oracle source; C-only patches are lifted (§7) |

**Change classes.**

- **Output-preserving:** the corpus must stay identical, and the check is automatic.
- **Output-changing:** an ADR under INV-LOSSLESS-DEFAULT, a new `hearth-c-ref@<tag>`, and an
  Owner-signed corpus re-baseline.
- **Contract-changing** (`hx_*.h`, `hearth.h`, FORMAT.md, NUMERICS.md): maintainer-only; re-derives
  the affected seams.

**Window protocol.** Windows open at every stage boundary [P5 risk 6], and in an emergency for a
security or correctness fix or an approved output change:

1. freeze the port branch;
2. merge upstream;
3. classify each upstream change by module state and change class;
4. port the deltas that touch Mithril-live or porting modules (an agent task whose spec is the C
   diff plus the corpus);
5. regenerate the C and run every gate of every completed stage;
6. re-baseline the corpus if, and only if, an ADR approved an output change;
7. sign the window record in the ledger;
8. unfreeze.

**Lineage.** `hearth-c-ref` is a lineage of tags, each with its own corpus, not one binary. The
"permanent differential oracle" is the newest tag, and older tags are kept for bisection.

**Recommendation.** Merge each stage to Hearth's `main` as soon as its gate passes, rather than
keeping a long-lived port branch. The generated module stays behind a CMake option until then.
Dual maintenance is the main cost of a strangler fig, and short-lived divergence keeps it to one
stage's worth of work [inference].

## 7. Reviewing generated C

INV-DEP is enforced "by review" (`INVARIANTS.md`). Under the recommended reading (§9.1), reviewing
generated C *is* how INV-DEP is enforced. The experience must therefore be designed, not left to
chance.

**What is checked in.** `.mith` sources and generated C side by side. Each generated file starts
with a provenance header:

- the `mithc` version and hash;
- the hash of the source closure;
- the canon version and the target profile;
- the line "do not edit; regenerate with `mithc`".

`#line` directives map back to `.mith` ([04-toolchain.md](04-toolchain.md)). The files are LF-only
under Hearth's existing `* text=auto eol=lf` rule (`.gitattributes`). Without that, byte-for-byte
regeneration would flap between Windows and POSIX checkouts.

**Emission rules** [target; enforced by `mithc` tests]:

1. **Deterministic.** The same inputs give the same bytes: no timestamps, and emission is ordered
   by definition path.
2. **Local.** Changing one definition changes only its own emitted region and its direct
   instantiations. CI reports any churn outside them as a diagnostic.
3. **Greppable.** C identifiers derive from `.mith` paths, and seam symbols keep their `hx_*`
   names.
4. **Readable.** Doc comments are carried over, there is one statement per line, there are no
   macro layers, and intrinsics look as they do in hand-written C. The output is canonical without
   any external formatter.

**Review flow.** A pull request presents:

1. the `.mith` diff, which is what gets reviewed;
2. the generated C diff, collapsed by `linguist-generated=true` in `.gitattributes`;
3. an evidence delta from `mithc ledger`: claims invalidated or re-established, audit verdicts,
   corpus and A/B results.

For kernels, the object audit validates the machine code, so C review weighs less. For non-kernel
code, C review stays meaningful, and rule 2 keeps it small.

**A C-only contributor patches a generated file.** The regeneration check fails with
`GeneratedFileEdited`. The diagnostic names the source definition and the next action:
`mithc lift --patch` proposes the equivalent `.mith` edit, with typed holes where undecided
([05-agent-protocol.md](05-agent-protocol.md)). The contributor's regression test is kept, and must
pass mutation testing (INV-VERIFY). Hand edits to generated C are never accepted, even temporarily:
they would break the INV-DEP argument. CONTRIBUTING.md should say so, and the generated directory
should have no human owner in `tasks.json`.

**Tooling.** `mutate.py` still works on generated C, with `#line` mapping mutants back to `.mith`
[R11 §5]. Crash triage uses symbol names traced to definition hashes
([04-toolchain.md](04-toolchain.md)).

## 8. Meanings and the numpy reference (INV-NUM-1/2)

**Two oracles answer two questions.**

- **The numpy reference** (`hearth.reference`, ADR-0005) answers "is this the model?". It is the
  ground truth for INV-NUM-1: logits within 1e-3·max(1, max|logit|) on F32 containers. It is the
  ground truth for INV-NUM-2: identical routing. It is itself cross-checked against `transformers`
  within 2e-3 relative.
- **NUMERICS.md and the C scalar code** answer "is this the canonical order?" (ADR-0003,
  INV-DET-3).

Mithril meanings take over the second role, never the first. Through S6, NUMERICS.md and the C
scalar code stay normative, and meanings must agree with them bit for bit (the corpus). After S6,
meanings become normative and NUMERICS.md is generated from them and checked [P5 §9.2 item 4].

**Rules that keep the reference independent** [inference, building on P2 §5.5 and RV D2-E]:

1. **No derivation in either direction.** `mithc lift` may lift from the C scalar code, never from
   `reference.py`. Independent versions already fail in correlated ways [RV: D2-E]; translating one
   oracle into the other would make the correlation total.
2. **Formulations may differ deliberately.** The engine's MLA is the absorbed form, algebraically
   equal to the reference but not rounding-identical (ADR-0003). The meaning keeps the absorbed
   form and the reference keeps the plain one, which strengthens the check.
3. **The fault model is run against meanings.** Each `numerics_v1` mutant (FMA contraction, tree
   shape, rounding, clamp, dropped scale, tie flip, NaN canonicalisation, RoPE style) is applied to
   a *meaning*. The record shows which of INV-NUM, the corpus and the C tests catches it. Mutants
   only bit-exact checks catch are the reference's listed blind spots. This tests D2-E's hypothesis
   that Hearth "hash-locks the weaker spec layer".
4. **INV-NUM-2 is exact.** Route equality is the sharpest intent check on the router meaning.
5. **Quantised paths have weaker oracles.** INV-NUM covers F32 only, and the Q4 comparison shares
   the quantiser with the code under test. Those paths rely on §2.4.

**In the ledger.** Agreement with the reference is a `quality` claim: measured on a hashed corpus
with a confidence interval, recording the residual distribution per architecture. It is never a
`refines` claim, because tolerance agreement cannot grade exactness. A port step that keeps the
corpus identical cannot move the residuals. A canon migration that changes the corpus must show
that residuals stay inside the INV-NUM bounds and report the shift ([03-trust.md](03-trust.md)).
[02-compute.md](02-compute.md) covers the meaning side of this relationship.

## 9. Constitutional decisions for Hearth's maintainers

None of these may be made by an agent. Hearth's tooling would let a contributor draft a new ADR,
with a maintainer merging (`governance/README.md`). These change what the engine *is*, so treat them
as Owner-only regardless.

### 9.1 Supersede ADR-0001; read INV-DEP with checked-in generated C (before S1 merges)

INV-DEP says "the engine core is C11 + OS APIs only: no third-party libraries, no C++ runtime, no
OpenMP", enforced by review. ADR-0001 gives the reasons: build with only a C compiler, keep the core
easy to audit, ship no runtime.

**Options.**

- **A (recommended, DR-026).** `.mith` sources and checked-in C11 live side by side. CMake builds
  from the C alone. CI checks byte-for-byte regeneration, and the C needs no runtime. INV-DEP holds
  literally, because what is compiled is C11.
- **B.** `mithc` becomes a build dependency. That changes INV-DEP; not during the port.
- **C.** No Mithril-sourced core: Mithril becomes tools over C, recorded as a design tombstone
  ([../DECISIONS.md](../DECISIONS.md)).

**Recommended ADR.** Supersede ADR-0001, keeping its pool and OS-isolation bullets verbatim and
adding option A's conditions as the reading of INV-DEP. Leave INV-DEP's text unchanged: it
constrains the compiled core, not where its source comes from.

**Breaker mechanics** (`governance/tools/adr.py:370-410`). Eight ADRs are Accepted at base.
Retiring ADR-0001 alone (12.5%) stays under the 15% churn breaker. Bundling it with an ADR-0004
supersession would trip it. Land each decision separately, with the Owner adding
`decisions-reviewed` explicitly.

**Later, at S6.** A separate ADR makes `.mith` meanings normative (§8).

### 9.2 GPU scope; `nvcuda.dll` or Vulkan (by-trigger, owner-gated)

**Facts** (measured [G03]): RTX 5070 with 12,227 MiB, compute capability 12.0, PCIe 5.0 x16, WDDM
driver. It drives the display (1,503 MiB at idle), and an AMD iGPU is also present. `nvcuda.dll`
and `vulkan-1.dll` are in System32, and there is no CUDA toolkit. ADR-0003 and task R01 already
require "bit-identical ... or documented tolerance".

**Decisions.**

1. **Is the GPU in scope for compute?** S0–S6b do not need it. The VRAM tier is reserved in the
   types from v0, so S4 must not hard-code two tiers.
2. **`nvcuda.dll` or Vulkan.** Driver-API CUDA with PTX text and explicit `.rn` is the shortest
   exact route here. Vulkan is exact only with `NoContraction` everywhere, the optional RTE and
   DenormPreserve features, and software division [G03]. **Recommendation:** rule `nvcuda.dll` an
   "OS API" for an opt-in tier, and treat Vulkan as later portability work.
3. **Move the display to the iGPU?** That frees about 1.5 GB.
4. **Tighten R01** to "bit-identical for any dynamically placed op", with tolerance only for
   opt-in static paths. Otherwise a VRAM expert cache breaks INV-DET-1 [G03].

**The gate is DR-022** (bands as in [../ARCHITECTURE.md](../ARCHITECTURE.md) §13 and
[../ROADMAP.md](../ROADMAP.md) §5 M7):

- *pass:* canonical expert GEMV ≥ 0.6x llama.cpp MMVQ on the same card [target], **and** end-to-end
  ≥ 2x CPU-only (measured), **and** logits hash-identical across placements;
- *amber* at 0.5–0.6x: one relayout campaign (scales split from the 34-byte blocks), then re-judge;
- *kill:* GEMV < 0.5x, or identity cannot be repaired. The outcomes are split, because rule C2
  ([02-compute.md](02-compute.md) §14) forbids `device(t)` values in placements decided at run time,
  and an expert tier is cache-driven (decision 4 above). A *speed miss with identity intact*
  (GEMV < 0.5x, or end-to-end < 2x) leaves the tier an opt-in `cross_device` profile, never a
  default, with a class-H tombstone and a hardware trigger. An *identity failure* allows only a statically placed,
  load-time-fixed GPU plan, as an opt-in `device(t)` lane with per-plan goldens and no cache-driven
  expert placement;
- ptxas and the driver JIT are in the trust base, with SASS graded `tested`;
- moving attention to the GPU needs validated canon/cr PTX transcendentals and a fixed-chunk
  attention order. That order redefines an existing op-DAG, so it is the major version `canon.v2`
  (by-trigger) and the first use of the major-version migration protocol, with bit-exact goldens
  reset ([02-compute.md](02-compute.md) §15.4, [03-trust.md](03-trust.md) §12);
- INV-DET-1 gains a device-placement axis only when a GPU tier exists.

## 11. Kimi-K3 and MXFP4

**Facts** [R06]:

- 2.8T parameters total, 104B active; 93 layers (69 KDA linear attention + 24 Gated MLA);
- Attention Residuals; LatentMoE with 896 experts, 16 active plus 2 shared, latent dimension 3584,
  expert dimension 3072;
- MXFP4 weights trained with QAT, and MXFP8 activations;
- one MXFP4 expert is 17,547,264 bytes, and a token touches about 25.8 GB of routed experts;
- the BF16 trunk is about 109 GB in kimi-k3-in-c's packing.

**What this PC can do, losslessly.** The BF16 trunk cannot be resident on 64 GB, and
INV-LOSSLESS-DEFAULT forbids requantising it by default. With about 50 GB of the trunk resident and
the rest streamed at Hearth's measured 7.16 GB/s demand-read rate [R11], the trunk alone costs
(109 − ~50) GB / 7.16 GB/s ≈ 8.2 s/token, so **≤ ~0.12 tok/s** [inference]. Routed experts then
stream with almost no cache left (25.8 GB / 7.16 GB/s ≈ 3.6 s more), which gives about 12 s/token
[inference]. kimi-k3-in-c reports 19.8 s/token at 64 GB against 5.6 s at 128 GB and above
(measured, project-reported [R06]).

The only route to a mostly resident trunk is an opt-in Q8 trunk: about 58 GB, at about 1%
reconstruction error per kimi-k3-in-c [R06]. That is **lossy**, so it needs a declared lossy profile
and cannot be the default.

**The simulator's figures are not comparable.** Hearth's simulator models K3 with every layer as
MLA, a Q8 backbone of about 31.7 GB per token, and latent projections FORMAT.md does not yet define.
On this PC it gives 0.36 tok/s NVMe-bound under LFU and a 1.04 tok/s ceiling with every *expert* in
DRAM (simulated, uncalibrated, synthetic trace; `docs/SIMULATOR.md` §8). Those numbers assume a
trunk about a third the size of the BF16 one, already quantised and resident; the 1.04 is
25.8 + 31.7 ≈ 58 GB/token at 60 GB/s. Neither is a lossless figure for a 2.8T model on 64 GB.

**Implications for the port** [inference unless cited]:

1. **One FORMAT revision, not three.** FORMAT v2 should bundle:
   - an MXFP4 block type (E2M1 elements, one E8M0 power-of-two scale per 32);
   - latent-projection tensors and KDA parameters;
   - per-slab content hashes, which also fix the mirror defect (§10).

   With S2 done, these are `format` description changes, not hand-written parser code. A format
   extension is one of B2's sealed task types, so K3 makes a natural maintainability test.
2. **Native MXFP4 is lossless; conversion to Q4 is not.** E2M1's non-uniform grid is not Q4's
   uniform int4 grid with an f16 scale per 64. Requantising would change outputs, while running the
   checkpoint's own format fits INV-LOSSLESS-DEFAULT [R06].
3. **canon.v1.1 (status: later) must fix the MXFP4 order before the first MXFP4 golden.** The scale blocks hold
   32 elements, but activation blocks hold 64. One option is two sub-block terms added in order:
   `acc += isum_a·(sa·dx); acc += isum_b·(sb·dx)` [P3 §9]. Twice an E2M1 value is an integer of at
   most 12 in magnitude, so a 32-element integer sum against Q8 activations is exact
   (|isum| ≤ 32·12·127 = 48,768 < 2^24). The E8M0 scale is a power of two. This is an *additive*
   canon change, the minor version `canon.v1.1`: it adds an order for meanings that do not exist
   yet, so existing meanings keep their hashes and evidence and no golden is reset. It is not the
   major `canon.v2` (fixed-chunk attention or explicit FMA, by-trigger), which is the first use of
   the major-version migration protocol ([02-compute.md](02-compute.md) §5,
   [03-trust.md](03-trust.md) §12). The format, copied verbatim from [02-compute.md](02-compute.md)
   §7.3, which owns `format` syntax:

   ```mith
   /// OCP MX v1.0 MXFP4: 32 E2M1 elements sharing one E8M0 power-of-two scale (17 bytes).
   format BlockMxfp4 {
       e: e8m0,                          // shared scale 2^(e - 127); special encodings per the spec
       q: e2m1x2<32>,                    // two E2M1 codes per byte; nibble order per source checkpoint
   }
   // Derived: size == 17 (checked); integer_view(i) = 2 * value(i) -> i32 with #[range(-12..=12)],
   // taking only {0, ±1, ±2, ±3, ±4, ±6, ±8, ±12}; exact dot meaning against ActQ8 sub-blocks.
   ```

   The T2 range obligation |isum| ≤ 48,768 < 2^24 makes the f32 cast exact
   ([02-compute.md](02-compute.md) §7.2).
4. **The trunk no longer fits.** About 109 GB of BF16 trunk breaks the dense-resident assumption
   on 64 GB, so dense layers must stream too (the bound above). In kimi-k3-in-c, a trunk-first
   budget split gave 1.69x at a fixed 128 GB budget, and its expert cache gave no gain below about
   36 GB of arena (measured, project-reported [R06]); neither result transfers to 64 GB as it
   stands. The tier split (trunk, expert cache, KV and KDA state) should be a tuned parameter, not
   a constant [R06]. S4's `StoreState` should key slabs by kind, not only
   by `layer·E + e`, in the same integer-handle style [G05].
5. **KDA changes rewind and rollback.** `hearth_rewind` truncates the KV cache, and failed calls
   restore position (`model.c:1321-1396`). KDA keeps a fixed recurrent state instead (about 626 MB
   in total in kimi-k3-in-c's sizing [R06]), so rewind needs snapshots. That is DR-025's snapshot
   API (status: later). S5's meaning must not hard-code "attention = KV cache". Chunkwise scans are
   in [02-compute.md](02-compute.md).
6. **Do not port a moving target.** K3 work landing in C during the port arrives through a rebase
   window (§6). Recommendation, at the Owner's call: K3 formats in Mithril after S2, kernels after
   S1.
7. **Another engine's determinism is not Hearth's.** kimi-k3-in-c accumulates in double precision
   with a fixed 4-way partition [R06]. Reusing its Apache-2.0 kernels would import that canon, so
   Hearth's R07-landscape task (`governance/tasks.json:353`) must treat it as a canon decision.

On this machine K3 is a storage- and trunk-bandwidth problem. For the port it tests formats, canon
migration and the snapshot API, not speed.

## 12. What Hearth gains even if Mithril stops

Most of the value lands in C Hearth before any `.mith` file ships. Each item survives a kill at any
milestone.

| Gain | Lands at | Survives because |
|---|---|---|
| ADR-0010: no platform libm in the output; a faster canonical `expf` (0.204 vs 1.12 ns/element, measured [G04]); cross-OS identity (INV-DET-4) becomes possible | S0 | It is C Hearth's own ADR |
| The cross-binary hash corpus catches libm, compiler and flag upgrades that change output | S0 | Golden-tier, owned by maintainers |
| The quantiser byte diff and the oracle-provenance rule close the oracle hole | S0–S1 | Plain tests and a review rule |
| The `numerics_v1` mutant pool, with G vs G+C vs T1 kill rates: whether the golden layer is the weaker spec [RV: D2-E] | M0 | A report, plus mutants usable by `mutate.py` |
| T1 certification of today's C kernels through the object audit: `validated` instead of `tested` | M0–M2 | The checker reads MSVC/Clang objects; no Mithril source is needed |
| A Zen-5-fuzzed semantics table for Hearth's instruction forms | M0–M2 | Reusable data ([03-trust.md](03-trust.md)) |
| Defect fixes: mirror hashes, the heat race, `struct_size`, the MXCSR guard (set and restore at every entry, assert at worker start), the decay drift, `n_io = 1`, a TSan job | S0–S4 | C changes |
| Hearth's history as tombstones, with tested resurrection triggers | S0 | A ledger directory plus a small tool |
| `timing_only` policy search on `hearth.sim` through an `hx_policy` shim [P4 §9.2] | M0 onward | Simulator-side; gains are expected to be small, and the durable win is assurance [RV: D2-A] |
| Every ported module as readable, checked-in C | each stage | Generated C compiles with no runtime. To detach a module, drop its `.mith` source and its regeneration check under an ADR, and maintain the C by hand |

The last row is why emission readability (§7) is a requirement and not a nicety. The exit from
Mithril must cost a deletion, not a rewrite.

## 13. Reviewer notes on the outline

- **Kimi band.** Reviewer note: the outline's "Kimi-class on one NVMe 0.8–2.9 tok/s, physics cap
  ≈ 3.4" is R08's figure for a *Kimi-K2*-class model (32B active). Kimi-K3 (104B active, about
  109 GB BF16 trunk) is heavier: losslessly, trunk streaming alone holds this PC to at most about
  0.12 tok/s [inference], and kimi-k3-in-c reports 19.8 s/token at 64 GB (§11). The
  simulator's 0.36 and 1.04 tok/s assume an all-MLA model with a smaller Q8 trunk and are not
  comparable. Sibling documents should say "K2-class".
- **`confined` versus DR-010, and exact slots.** Resolved: [03-trust.md](03-trust.md) §2.2 gives
  non-kernel logits-path code its own admissibility row. 03 §3.2/§3.4 read "`confined` admits proof
  only" as a constraint on the evidence *form* (a T0 verdict on the binary): its effective grade is
  `validated(partition)` from table premises, and for `confined(S)` `validated(bounded)` via the
  store-core theorem; the code floor, `tested`, is printed beside it and not met.
- **`struct_size` timing.** Reviewer note: DR-020's "S6a: export hearth.h exactly, + struct_size"
  can satisfy both "exactly" and "Python toolkit unchanged" only if `struct_size` lands in C Hearth
  first. This document puts it at S0, with the R3 commit.
- **The circuit breaker.** The proposals say a Mithril core "trips the circuit breaker". Under the
  recommended reading it does not (§9.1), so the Owner must enforce the decision's constitutional
  status.
