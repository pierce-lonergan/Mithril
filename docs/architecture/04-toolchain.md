# 04 — Compiler, backends and runtime

`mithc` is an untrusted compiler, written in Rust, wrapped around a small trusted core. Text is the
source of truth; hashes are the identity. It is a query database keyed by content hashes. Its
persistent tier is the evidence ledger, and every phase emits relations into a Datalog **Fact
Plane**. The pipeline runs Syntax → HIR → THIR → MIR (= MCore) → KIR. It emits strict C11 for all
code. That C is checked into the consuming repository and regenerated byte for byte in CI (DR-026).
For the roughly 20 hot kernels, the machine code that MSVC or Clang actually produced is decoded,
lifted and matched against the exact meaning (the **object audit**, B1.5; DR-008). Variants that do
not match are never dispatched in a release build. A direct x86 emitter is built only if a trigger
fires (DR-009). The GPU expert tier comes first if the audit covers at least 95% of dispatched
variants. This document fixes the C11 lowering rules, the audit pipeline, the runtime layer
(`std_platform`), debugging and profiling, latency budgets, how assurance works for non-kernel code,
how agents build and check `mithc` itself, and why self-hosting waits until after M7. Language
semantics are in [01](01-language.md), kernels and schedules in [02](02-compute.md), the trusted
core and T1 rule list in [03](03-trust.md), the agent-facing verbs in
[05](05-agent-protocol.md), measurement in [06](06-forge.md) and port gates in
[07](07-hearth-port.md).

## 1. Conventions and principles

**Status labels** (the mapping of [ROADMAP §1](../ROADMAP.md) rule 7):
- `v0`: in the `mithc` that ports Hearth, milestones M1–M5. Where the milestone matters it is
  given, e.g. `v0 (M2)`. M0 experiments that feed v0 (X0, X2) are written `v0 (M0)`.
- `v1`: present by Edition 1, milestones M6–M7.
- `later`: planned after M7.
- `reserved`: present in schema and types but not producible yet.
- `by-trigger`: built only when its trigger in the ROADMAP §9 deferral register fires (IDs such
  as D-12 below are ROADMAP IDs; P5's own register is cited as [P5 §13]).

Where a label here and a milestone in [ROADMAP §5](../ROADMAP.md) disagree, the milestone governs.
[ROADMAP](../ROADMAP.md) owns the dates. Numbers are labelled measured, simulated, [inference] or
[target]. Every `.mith` snippet uses provisional syntax until the Surface Lab decides
([05](05-agent-protocol.md)). Snippets follow the subset rule (DR-002). C snippets show emitter
output and are illustrative.

**Tier names.** This document splits T0 in two, because the halves carry different evidence:
- **T0-src** is the front-end judgement in THIR: types, effects, capabilities, ownership,
  second-class references, grades. It rejects programs, but its evidence is graded `tested` until
  mechanised (DR-010). For policy and evolve code it is advisory, and T0-bin decides.
- **T0-bin** is the object-level confinement decision procedure for `timing_only` policy and
  evolve code (§7.2). Its verdict is `proof` in form for `confined` claims, and its effective
  grade meets its premises ([03](03-trust.md) §3.2, §3.4): effective `validated(partition)` from
  table premises; for `confined(S)`, `validated(bounded)` via the store-core theorem; code floor
  `tested`, printed, not met.

**Toolchain principles** (refining [ARCHITECTURE §3](../ARCHITECTURE.md)):
1. **Untrusted producer, trusted checker.** Parser, type checker, lowering, schedules, C compilers
   and agents are untrusted; the one front-end exception, the elaboration of exact meanings into
   KIR, is a graded code component (§2). Correctness evidence comes from small checkers that replay
   certificates [R07 §9]. "Unknown" is a rejection.
2. **Text is the truth, hashes are the identity** [P5 §1]. Formatting alters no identity [P1 §2].
3. **Deterministic toolchain.** Same inputs, same bytes (C, maps, facts, diagnostics) on any host
   OS, because checked-in C is verified by regeneration.
4. **Validate the output, not each rewrite.** Schedules supply correspondence maps; hand-written
   intrinsics and generated schedules face the same check [P5 §4].
5. **No hidden runtime.** Generated code links only to the audited `std_platform`: no GC, no
   unwinding, no global initialisation [R11 P0 #9].
6. **Check the machine code that runs.** Compilers can contract or reassociate behind the flags'
   backs [R07 §10], so kernel evidence attaches to the object and cheap binary scans cover the rest.

## 2. The pipeline and its IRs

```
 .mith text ──(Lark-conformant, error-tolerant parser)──► Syntax   lossless CST; anchors; fmt round-trip
   ──► HIR    names resolved, desugared; holes (todo!) as typed nodes; def/interface hashes
   ──► THIR   types, effect rows + capabilities, ownership/borrows, projections, fidelity grade,
              determinism scope, refinement obligations ──► diagnostics (grouped) + fixes
   ──► MIR    (= MCore) small normative core: monomorphised, moves/borrows/consumes explicit,
              capabilities as parameters ──► mithi (independent interpreter: oracle, comptime)
        ├──► C emitter (B1): destination passing, check elision, restrict, #line ──► C11 text
        └──► KIR  kernel fns only: index loop nests + layouts + explicit FP op-DAG + integer
                  subterms (+ ranges) ──apply schedule──► scheduled KIR + correspondence map
                  ──select──► LIR (SSA over semantics-table ops, keyed by XED iclass)
                       ├──► C11 intrinsics (B1)       ├──► x86 encoder (B3, by trigger)
                       └──► PIR (PTX subset, B2, owner-gated)
 object code ──XED decode──► LIR′ ──T1/T2 vs KIR meaning──► witness ──mithcheck replay──► ledger
 every phase ──► Fact Plane relations (typed, keyed by content hash)
```

- **Syntax** `v0`. Lossless, so `mithc fmt` and the hash-anchored edit protocol round-trip. The
  hand-written parser is conformance-tested against the normative `mithril.lark` [P5 §3.1].
- **HIR** `v0`. Holes are typed nodes; programs with holes still check and run (DR-003).
- **THIR** `v0`. The rejecting phase: types, effect rows as capability parameters, second-class
  references with projections and the non-escaping kind (DR-004), grades, determinism scope, and
  `requires`/`ensures`/`#[range]` obligations (DR-011). These judgements are T0-src (§1), graded
  `tested` until mechanised (DR-010).
- **MIR = MCore** `v0`. The normative core of [01](01-language.md). Store, policy, parser and API
  code stay here until emission. Byte and time views of the same code (cost signatures,
  [02](02-compute.md); with `mithc explain`, `v0 (M2)`) are further interpretations of MCore,
  not a separate IR [P1 §4].
- **KIR** `v0`. `kernel fn` bodies only, as the exact meaning. Schedules are DAG-preserving
  KIR→KIR rewrites with licence tags (`exact`, `int_assoc`) that emit the correspondence map T1
  consumes [P3 §4].
- **LIR** `v0`. Instruction-level SSA over rows of the owned x86 semantics table. It has three
  producers: instruction selection for B1 kernels (each op prints as one intrinsic), the object
  lifter (B1.5, producing LIR′) and the direct emitter (B3). An intrinsic with no table entry
  cannot be written [P5 §3.3].
- **PIR** `later`, owner-gated. A PTX subset with explicit `.rn` (DR-022).

The C emitter's lowering steps (destination passing, check placement, `restrict`) are internal,
not a normative IR.

**`mithi` and MIR.** DR-010 makes `mithi` the differential oracle and comptime evaluator.
Independence is the point, so it has two modes:
- *Independent mode* (the oracle) has its own parser and checker, built from the Lark grammar and
  the normative core, sharing no lowering code with `mithc` (~4–6k lines [inference, P5]).
- *MIR mode* interprets `mithc`'s serialised MIR. It is used only to localise a disagreement to
  the front end or the back end.

**Elaboration is trusted, and graded.** A comptime bug in `mithi`, or a mis-elaborated meaning,
would change both sides of T1 consistently, so T1 cannot catch it. The elaboration of exact
meanings into KIR, comptime included, is therefore a code component of the trust base, graded
`tested`. It sets only the code floor, not the effective grade, so DR-021 holds ([03](03-trust.md)
§3.4, §14). The mitigation: kernel-reachable comptime values are recomputed at build by a second
evaluation path that shares no front end with `mithi` (the comptime code compiled through B1 and
run natively [inference]), and byte equality is required; `mithi` also runs the meaning
differentially on the hash corpus (§12). An independent kernel-subset extractor inside `mithcheck`,
which would take elaboration out of the trust base, is `by-trigger` (ROADMAP §9).

## 3. Query database and content addressing

**Identities** `v0`. All persisted identities use SHA-256. Anchors display 8 hex digits
(`store::evict::victim@3fa09c1e`) [P5 §7]. Each hash kind has its own domain prefix.

| Hash | Covers | Changes when | Used for |
|---|---|---|---|
| definition hash | normalised AST: locals alpha-renamed, references replaced by the targets' *interface* hashes; comments and formatting excluded | the body or signature changes | edit anchors, Forge dedup, cache keys |
| interface hash | signature: types, effect row, grades, contracts, layout | the visible summary changes | early cutoff: callers are re-checked only when it changes [P1 §4] |
| closure hash | definition hash plus the closure of dependency *definition* hashes | anything that can change behaviour changes | ledger keys for behavioural claims |
| toolchain hash | `mithc` build, semantics table, rewrite list, `mithcheck`, `std_platform`, and each C compiler identity (version plus binary hash, path-independent) with its flag set, edition | any of those changes | part of every ledger key, so upgrades invalidate nothing silently [P2 §4] |
| audit key | closure × schedule × target × toolchain hash × compiler × flags | as its parts | cached audited objects (§11) |

Doc comments are excluded from the definition hash and get a separate doc hash. Context packs
need it, and it keeps model-read prose apart from code identity. The prompt-injection boundary is
in [03](03-trust.md).

**Ledger keys.** A claim is keyed by `H(code closure, spec, toolchain, target, hw fingerprint)`
([03](03-trust.md)). Proofs and validations carry no hardware fingerprint, so
they are reused on another machine. Measurements carry one, so they are not [P4 §4].

**Queries** `v0`. Salsa-style memoised queries with red-green re-validation and early cutoff
[R09 §6]:

```
parse(file) · items(file) · def_hash(item) · iface_hash(item) · thir(item) · effects(item)
grades(item) · obligations(item) · facts(item) · mir(item) · kir(kernel)
apply(kernel, schedule, target) · lir(kernel, target) · t1(kernel, target) · t2(obligation)
c_unit(module, target) · object(c_unit, compiler) · audit(kernel, target, compiler)
cost(item, profile) · map(c_unit)
```

The expensive queries look in the ledger before they compute: `t1`, `t2`, `audit`, mutation
scores and measurements [P3 §4, P5 §4]. A stale result is reported, never silently reused.
Inputs that rarely change (std, the semantics table, compiler identities) are marked
high-durability, so a body edit never re-validates them. `mithc serve` keeps the database warm for
the CLI, MCP and LSP ([05](05-agent-protocol.md)).

**Determinism rules for `mithc` itself** `v0` (the precondition for DR-026):
- No output depends on hash-map iteration order. Everything emitted is sorted by module path, then
  source order.
- No timestamps and no absolute paths. Paths are relative to the package root, with forward
  slashes and LF line endings.
- Parallel query execution joins results in a fixed order. Thread count never changes output.
- CI runs `mithc` twice on Windows and once on Linux and compares all emitted bytes. A difference
  is a release-blocking bug.

## 4. The Fact Plane

The Fact Plane is the compiler's queryable record: typed relations emitted by every phase, keyed by
content hash, and maintained incrementally per definition [RV: S16].

**Relations** (`v0` schema, versioned as part of the spec). Examples:

```text
defines(def, module)            calls(f, g, span)             uses_effect(f, effect)
grade(f, fidelity, scope)       cap_flow(src, dst)            unsafe_site(f, span)
det_boundary(f, evidence)       kernel_variant(k, target, schedule)
param(f, p, kind)               copy(f, site, bytes, origin)  check(f, site, kind, status)
c_symbol(sym, def, variant)     audit(k, target, compiler, verdict)
evidence(claim, grade, key)     env(name, value)              hot_root(f)
```

**Rules.** The kernel is the terminating fragment of Datalog: stratified negation, aggregates and
user lattices. Rules outside it are rejected [RV: S16]. For example, the hot-path relation and the
hidden-copy check of §6.5 are four rules:

```text
// Fact Plane rules (spelling provisional)
hot(F) :- kernel(F).        hot(F) :- par_for_body(F).        hot(F) :- hot_root(F).
hot(G) :- hot(F), calls(F, G, _).
violation(hidden_copy(F, S, B)) :- hot(F), copy(F, S, B, introduced_by_lowering), B > 64.
```

**Consumers:** `mithc why` and `ledger why --trust-base` ([03](03-trust.md)); invariants as rules
(e.g. INV-DET-3's "no fused multiply-add in canonical code") [RV: S16]; lints and refactor
preconditions; the incremental trigger evaluation behind `mithc revisit` ([06](06-forge.md)); the
audit variance matrix (§8); the generated-C review summary ([07](07-hearth-port.md)).

**Status and limits.** Relation emission and a fixed rule set (above, plus ledger invalidation and
triggers) are `v0`, on a small embedded evaluator (Ascent, a Rust Datalog engine from [RV: S16],
is a candidate). User-written `invariant` rules and an incremental engine are `by-trigger`
(ROADMAP D-12, from [P5 §13]: > 20 custom lints, or trigger scans exceed the edit-loop budget).
The Fact Plane never sits on the type checker's hot path; Polonius and chalk are the warning
[RV: S16]. Experiment E3 measures incremental latency. If evaluation is not
interactive, rules run at `mithc check --full` and in CI, not per keystroke. Experiment E1
(Hearth's four "enforced by review" invariants as CodeQL/Soufflé queries) can run before `mithc`
exists.

## 5. Backends B1–B4 and sequencing rules

| ID | Backend | Scope | Kernel evidence | Status |
|---|---|---|---|---|
| — | `mithi` (interpreter) | everything: oracle, comptime, fast test runs (§11) | reference | `v0` |
| B1 | **strict C11** | all code; the Hearth port target | `validated(LIR)` before compilation; tested binary | `v0` |
| B1.5 | **object audit**: XED decode of MSVC/Clang kernel objects → LIR′ → T1/T2 | the ~20 hot kernels × ISA × shipping compiler | `validated(object)`, required for release dispatch (DR-008) | `v0 (M2)` |
| B2 | **PTX expert tier** (PIR → PTX, `cuModuleLoadData` via `nvcuda.dll`) | expert GEMV and the ops placed with it | `validated(PTX)`; the SASS level is `tested`, ptxas and the driver are in the trust base (DR-022) | `later`, owner-gated |
| B3 | **direct x86-64 kernel emitter** (LIR → XED encoder → COFF/ELF) | the staged-kernel subset only | `validated(object)` by construction | `by-trigger` (DR-009) |
| B4 | **copy-and-patch JIT** for load-time residuals | stencils built AOT by B1 and audited with holes as parameters | as B1.5 plus T2 on hole ranges | `by-trigger` |
| — | LLVM IR backend | optional | never trusted; T1 judges outputs, so a backend adds no trust [P2 §4] | `later`, optional |

Cranelift lists SIMD as unsupported in rustc's backend, and QBE has no vector types [R09 §8]. Neither
is on the path.

**Sequencing rules.**

1. **B1 first, for all code** (M1). C11 matches Hearth's toolchain and INV-DEP, and links module by
   module behind the `hx_*.h` seams [R09 §8], [R11].
2. **B1.5 after census and spike** (DR-008). First X0: the census of what MSVC, Clang and GCC emit
   (§7.1). Then X2: T1 on transliterated intrinsic IR with correspondence maps. Then the object
   audit of the hot kernels at M2.
3. **Decision point at M2 exit: audit coverage.** Coverage is the fraction of *dispatched
   variants* (kernel × ISA target × shipping compiler of the release profile) that hold
   `validated(object)` evidence. The Fact Plane computes it from `audit` and `kernel_variant`.
   - **≥ 95%.** The audit gives the emitter's assurance without the emitter. B2 comes before B3,
     if the owner admits the GPU (DR-022). B3 is recorded as a scoped tombstone (class E), with
     DR-009's triggers as its resurrection condition [P3 §4].
   - **90–95%.** Each failing variant is triaged. A rule or table gap is fixed within the rule
     budget ([03](03-trust.md)). An unpinnable compiler rewrite fires DR-009 *for that kernel
     only*.
   - **< 90%.** The M2 kill applies: the validated-identity claim is dropped and the project is
     re-justified [P5 §10.2], [ROADMAP](../ROADMAP.md).
4. **B3 only by trigger** (DR-009), in either of two cases:
   - An *unpinnable compiler rewrite*: no flag, intrinsic choice or source shape prevents a
     T1-failing sequence across the pinned compiler versions.
   - A ≥ 5% kernel gap attributable to codegen. This is measured with e ≥ 20 (DR-018) against a
     T1-validated alternative. The lifter validates a hand-written assembly prototype just as it
     validates compiler output, so the alternative is cheap to produce.

   B3 is never built for bandwidth-bound decode GEMV, which sits about 56× below the Zen 5 ridge
   [R08 §7.2].
5. **B4 only if** load-time specialisation (`@bind(load)`, deferred) shows ≥ 10% decode or prefill
   gain in a C go/no-go experiment (an [inference] threshold), **and** the ahead-of-time variant
   count exceeds what can be shipped (ROADMAP D-04, from [P5 §13]). Stencil pages follow W^X and
   are flushed with `FlushInstructionCache` on Windows. Code is swapped only through versioned
   dispatch tables at quiescent epochs, never patched in place (§9.2, hot-swap).

**B2** ([02](02-compute.md) has the design): exact int32 block sums (dp4a) plus an ordered
`add.rn` epilogue, loaded from `nvcuda.dll`, T1 against a small PTX table, gated by DR-022.

## 6. C11 lowering rules (B1)

These rules are normative for the emitter. Each one is a checkable property. The Fact Plane and
the binary scans check them, so a violation is a `mithc` bug, not a style issue.

### 6.1 Dialect, toolchains and the helper header `v0`

- ISO C11, with no compiler extension except through `mith_canon.h`. That header holds only
  `static inline` helpers and macros, much like Hearth's `hx_platform.h`. It is generated, checked
  in and versioned with the toolchain hash. It is not a runtime library. Its per-compiler macros
  include `MITH_RESTRICT` (§6.4), `MITH_FORCEINLINE` (§6.7), `MITH_VECTORCALL` and
  `MITH_FP_CONTRACT_OFF` (below).
- Every generated translation unit begins with a provenance header, then `#include
  "mith_canon.h"`, `MITH_FP_CONTRACT_OFF` [P3 §4] and `_Static_assert(FLT_EVAL_METHOD == 0, ...)`.
  x87 evaluation never occurs.
- **`MITH_FP_CONTRACT_OFF`** expands per compiler, because no single spelling is warning-free
  everywhere: `_Pragma("STDC FP_CONTRACT OFF")` on Clang; `__pragma(fp_contract(off))` on MSVC,
  whose documented spelling this is (the `STDC` form draws C4068 on toolsets that do not
  recognise it); and nothing on GCC, which does not implement the `STDC` pragma and would warn
  under `-Wall` (`-Wunknown-pragmas`). The macro is belt and braces. What is relied on is the
  pinned flags (§6.2, `-ffp-contract=off` on GCC and Clang) and the contraction scan.
- Struct layouts carry `_Static_assert(sizeof(T) == N)`, as Hearth does today (`hx_block_q4` is
  34 bytes, `hx_act_q8` 72). All targets are little-endian, and this is asserted per compiler in
  `mith_canon.h`.
- Generated code compiles warning-free at the consuming project's warning level.

### 6.2 Strict FP flags per compiler `v0`

| Compiler (version pinned in `mith.lock`) | Required | Forbidden anywhere in the build of a Mithril TU | ISA translation units |
|---|---|---|---|
| MSVC `cl` (VS 2022 or later) | `/std:c11 /fp:precise /experimental:c11atomics /utf-8` | `/fp:fast`, `/fp:contract` | `/arch:AVX2`, `/arch:AVX512`, per file only |
| Clang (incl. Apple clang) | `-std=c11 -ffp-contract=off -fno-fast-math` | `-ffast-math`, `-Ofast`, `-ffp-contract=on`, `-ffp-contract=fast`, `-fassociative-math`, `-freciprocal-math`, `-ffinite-math-only` | `-mavx2 -mfma -mf16c`; `-mavx512f -mavx512bw -mavx512vl -mavx512vnni`, per file |
| GCC | `-std=c11 -ffp-contract=off -fno-fast-math` | as Clang | as Clang |

Why: MSVC `/fp:precise` stopped contracting only in VS 2022 [R11 §2]; Clang's C default
`-ffp-contract=on` fuses within a statement, and GCC defaults to `fast` outside ISO modes
[R09 §8]. ISA flags are per file (as in Hearth's CMake), so AVX-512 cannot leak into portable code.
Under `/fp:fast /arch:AVX2` MSVC vectorises `expf`/`sinf` into `__vdecl_*`, and 51% of `expf`
results on [-10, 10] then differ from scalar UCRT by up to 3 ulp (measured [G04]). Exact code calls
no platform libm (DR-014), and the forbidden list closes that path.

**Flags are necessary, not trusted.** The emitter writes a build fragment (CMake, as Hearth uses)
with these flags. A CI *flag audit* reads `compile_commands.json` and rejects any Mithril TU built
without them. Kernel objects then face the audit (§7). Every other object from an exact-graded TU
gets a *contraction scan*: XED-decode every function and reject any FMA-class iclass that the map
file (§6.8) does not trace to an explicit `fma`. On arm64 the scan looks for FMADD/FMLA-class
instructions (§8). It reuses the audit's decoder, so it costs almost nothing [inference].

**Exact operations.** Each canonical float operation becomes one C statement with a named
`const` temporary, so order is explicit in the text and the map. Explicit `fma` lowers to the
target's fused-instruction intrinsic; a target without one cannot host exact code that uses `fma`
(compile error). `sqrt` lowers to the IEEE instruction, never libm, so errno cannot matter.
`canon::nan` lowers to an unordered compare plus select (Hearth's `mask_mov` pattern).
Transcendentals lower to `cr::` or `canon_v1::` code emitted from Mithril (DR-014).

### 6.3 UB-free integer and memory lowering `v0`

Generated C never relies on undefined behaviour. CI builds it with UBSan [R11 P0 #18].

- **Signed overflow.** Where T2 or a range fact proves it absent, plain signed C arithmetic is
  emitted. The C is then UB-free *because of* the proof, so T2 is in the trust path for that
  property. Otherwise the operation is checked (a compiler builtin, or portable widen-and-compare),
  and a failed check is a trap ([01](01-language.md) §12). `wrapping_*` lowers to unsigned arithmetic. Converting back to signed is
  implementation-defined in C11, not undefined; two's complement is asserted in `mith_canon.h`.
- **Shifts.** The amount is proven or checked. Left shifts of possibly negative values happen on
  unsigned types; UBSan caught exactly this in Hearth's bf16 load [R11 P0 #18].
- **Float→int `as`** keeps Rust semantics (saturate, NaN→0 [P5 §3.1]). It lowers to an explicit
  saturating sequence, never a bare C cast of an unproven value, because out-of-range conversion
  is UB in C. Kernels use range-proved conversions.
- **Aliasing and alignment.** Bit-casts use fixed-size `memcpy` of ≤ 64 bytes (register moves).
  Unaligned data such as 34-byte Q4 blocks is read through `loadu` intrinsics or `memcpy`, never a
  cast pointer.
- **Initialisation and races.** Definite initialisation is checked in THIR. Atomics exist only in
  `std_platform`.

### 6.4 `restrict` from alias facts (DR-027) `v0 (M2)`

Under mutable value semantics a `&mut` parameter is exclusive for the call, and references cannot
be stored or returned except through projections (DR-004). So no other parameter overlaps a
`&mut` parameter. Shared `&` parameters may overlap each other, and for most types nothing writes
them while the borrow lives. C11 §6.7.3.1 constrains `restrict` only for objects that are
modified, so borrow-derived pointers are marked: `T *restrict` for `&mut`, `const T *restrict` for
`&T` where `T` is free of interior mutability (below), and the same for disjoint projections such
as `pool.for_chunks` slices. The emitter uses a `MITH_RESTRICT` macro, as Hearth uses
`HX_RESTRICT`. Raw pointers inside `std_platform` and `foreign` parameters never get it.

**The interior-mutability exclusion.** User code has no `Cell` or `RefCell` (FF-CELL,
[01](01-language.md)), but `std_platform` types are written *through shared references*:
`&Mutex<T>` by `with_lock`, `Condvar` by waits and notifies, `Frozen<T>` by its refcount
(wherever the implementation places it), and capability or service handles may front mutable OS
state. If an object reached through a
`const T *restrict` is modified by any means, C11 §6.7.3.1 makes the access undefined, so
`const T *restrict` on such a `&T` would be a latent miscompile. The rule:
- A derived kind, provisionally `NoInteriorMut` (the analogue of Rust's internal `Freeze`; name
  and spelling are owned by [01](01-language.md) §5.7), holds for a type iff every field holds it,
  transitively. Primitives, arrays and slices of such types have it. `std_platform` types do not,
  unless `std_platform` asserts it by hand, as it alone may for `Send` and `Sync`. `Mutex<T>`,
  `Condvar`, `Frozen<T>`, atomics, and pool, service and file handles never assert it.
- `&T` with `T: NoInteriorMut` lowers to `const T *restrict`. Any other `&T` lowers to plain
  `T *`: no `restrict`, and no `const`, since `std_platform` writes through it.
- `&mut T` keeps `T *restrict` for every `T`: exclusivity covers the object itself, and
  refcounts or OS state reached through a pointer stored inside it are not "based on" the
  parameter, so `restrict` does not constrain them.
- The kind is recorded in the `param(f, p, kind)` fact, so `mithc why` explains a missing
  `restrict`.

**What this buys, honestly.** Hearth's portable `value_sum` already has hand-written `restrict`,
which its own comment credits with letting compilers vectorise it ("MSVC/SSE2: ~15% faster", a code
comment, not a ledgered measurement). It runs at 18.0 GMAC/s against 94 GMAC/s for a bit-identical
register-blocked AVX-512 prototype (measured [R11 §3]). That 5× gap is a *schedule* gap, closed by
an exact F1 schedule ([02](02-compute.md)), not by `restrict`. What Mithril adds is `restrict`
everywhere, correct by construction, including code nobody annotated. Its effect on generated C is
measured per port stage, not assumed.

**Risk.** A wrong `restrict` is UB, so a front-end exclusivity bug becomes a miscompile. Test
builds add *alias assertions*: a range-overlap check at entry to every function with `restrict`
parameters, which traps ([01](01-language.md) §12), naming the definition hash. `mithi` differential runs (§12) use them.
A missing interior-mutability exclusion is the same class of bug, so `std_platform`'s audit
checks that every type it writes through a shared reference lacks `NoInteriorMut`. Until T0-src
is mechanised, `restrict` soundness is graded `tested`.

### 6.5 MVS values: out-parameters, and no hidden copy above N bytes `v0 (M2)`

The rule: **every copy in the emitted program is either written in the source or recorded and
justified. On hot paths, a copy introduced by lowering that exceeds N bytes is a compile error.**
N is 64 bytes [target], one cache line. It can be configured per profile in `mith.toml`.

Lowering obligations:
1. **Returns.** Scalars, SIMD vectors and aggregates of ≤ 8 bytes return by value. Anything larger
   lowers to a caller-provided `T *restrict out` that receives the final destination: `let y =
   f(x)` becomes `f(x, &y)`, and `rows[t] = f(x)` becomes `f(x, &rows[t])`. Copy elision is
   guaranteed by construction. The 8-byte cut follows Win64, which returns only 1/2/4/8-byte
   aggregates in registers [inference: ABI fact; SysV and AArch64 allow 16]. SIMD vectors cross a
   boundary by value only where it is inlined away (kernel helpers, §6.7) or the function is
   `MITH_VECTORCALL` (`__vectorcall` on MSVC, empty elsewhere): MSVC's default x64 convention
   passes `__m256`/`__m512` arguments through a hidden pointer to a caller-allocated copy.
2. **Arguments.** Aggregates over 8 bytes are never passed by value in C, because Win64 and SysV
   would copy them behind the source's back. `&T` becomes `const T *restrict` (plain `T *` when
   `T` has interior mutability, §6.4), `&mut T` becomes `T *restrict`, and a moved aggregate
   becomes a pointer to caller storage that is dead after the move.
3. **Overlapping destinations.** If the destination overlaps an argument, lowering would need a
   temporary and a copy. On hot paths this is rejected with an in-place fix. Elsewhere the
   temporary is emitted and recorded as a `copy` fact with origin `introduced_by_lowering`.

```mith
struct KvRow { v: [f32; 1024] }                          // 4 KiB value type

fn decayed(row: &KvRow, f: f32) -> KvRow { todo!("decayed") }

fn tick(rows: &mut [KvRow], i: usize) {
    rows[i] = decayed(&rows[i], 0.5);
    // Legal Rust, same meaning. On a hot path mithc rejects it: the out-parameter &rows[i]
    // overlaps the argument, so lowering needs a hidden 4,096-byte temporary. Offered fix:
    //     fn decay(row: &mut KvRow, f: f32)    and    decay(&mut rows[i], 0.5);
}
```

**Hot** means reachable from a `kernel fn`, a `par for` body, or a `hot_roots` entry in
`mith.toml` (for Hearth, the per-token forward entry). The Fact Plane rules of §4 compute it; no
surface syntax is added. **Two checks** apply. At MIR, every copy node carries its size and origin,
which guards the untrusted lowering. At object level, hot functions are scanned for `memcpy` or
`memmove` calls, `rep movs` and synthesised copy loops (C compilers emit them for struct
assignment), and each hit is matched against the recorded copies. An explicit `.clone()` of a
large value on a hot path is a warning, not an error, because it is the program's meaning.

### 6.6 Bounds and overflow checks: elision and a measured tax budget `v0`

- **Kernels.** A bounds or range obligation that cannot be proven is a compile error, never a
  runtime trap (DR-011). A trap in a memory-bound GEMV inner loop can defeat vectorisation [panel:
  systems]. Three one-past writes into register-allocated SIMD arrays escaped every tool Hearth had
  [R11 P0 #17], so static proof is a correctness feature too.
- **Non-kernel code.** Indexing and arithmetic are checked with Rust meaning. A failed check is a
  trap ([01](01-language.md) §12): a trap ends its fail domain (01 §12.2); it never unwinds and
  never aborts the host. Checks are elided in three ways:
  1. **T2 and range facts:** `for i in 0..xs.len()`, `requires`, `#[range]`, format-derived
     bounds.
  2. **Loop versioning:** test the maximum index once before the loop. If it passes, run a
     check-free body. Otherwise run the checked body. Semantics are exactly preserved, including
     *which* iteration fails and any effects before it. Plain hoisting would change observable
     `io` before the failure, so it is used only when the loop body has an empty effect row.
  3. **Rust-coincident idioms** suggested by diagnostics, such as `chunks_exact`-style iteration
     with the same meaning as Rust's.

  User code has no unchecked escape hatch. `get_unchecked`-class operations exist only under the
  `unsafe` grant, which only `std_platform` holds.
- **The tax budget.** A 1% end-to-end effect cannot be certified at the plan's own statistics.
  [06](06-forge.md) §6.6 gives n ≈ 12·σ_d²/δ² blocks. At δ = 1% that is 48 blocks at σ_d = 2%,
  about 6.4 quiet hours per configuration per stage for end-to-end decode (8-minute blocks), and
  192 blocks, about 26 h, at σ_d = 4% [inference]. Hearth's decode is noisy (19–22 tok/s,
  measured), so the larger figure is plausible. Either costs more than the 3% parity gate the
  budget is meant to protect. The tax is therefore measured where it is resolvable, per port
  stage:
  1. **Static count** (no machine time). The Fact Plane joins residual `check(f, site, kind,
     status)` facts with `hot(f)` and weights each site by its trip count per unit of the stage's
     work (per token for S5, per dispatch for S3, per file for S2). Trip counts come from
     cost-signature loop bounds where known, and otherwise from a counting build (never shipped)
     run on the stage's golden workload. A residual check that blocked vectorisation is a work
     item whatever its count.
  2. **Microbenchmarks** of each hot function the count flags. Single-thread, the default build
     runs against a measurement-only build with checks forced off (never shipped), interleaved and
     load-gated per DR-018. The anytime-valid upper confidence bound on the tax must be **≤ 1%**
     [target]. At [06](06-forge.md)'s 40-second microbenchmark blocks this costs about 32 min per
     function at σ_d = 2% and about 2.1 h at σ_d = 4% [inference].
  3. **End to end, only DR-018's 3% gate.** Non-inferiority against `hearth-c-ref` stays the hard
     gate (tok/s for S5, dispatch latency for S3, parse time for S2), and there is no separate
     end-to-end tax test. The per-function 1% keeps checks from consuming the 3%.

  Expected quiet-hour cost per stage: none for the static count, plus about 0.5–2 h per flagged
  function [inference]. The M0 measurement of σ_d per run type ([06](06-forge.md) §6.6) replaces
  these illustrations.
- **Visibility.** `mithc explain --checks <item>` lists residual hot-path checks and flags those
  that blocked vectorisation (from MSVC `/Qvec-report:2`, Clang `-Rpass-missed=loop-vectorize`).
  A stage over budget gets a work item, not a waiver.

### 6.7 Kernels, ISA translation units and dispatch `v0`

- Each schedule variant goes in its own TU, compiled with that ISA's per-file flags (Hearth's
  pattern). Its symbol is registered in a generated dispatch table.
- **Kernel helpers are forced inline.** C `static inline` does not guarantee inlining, and a
  helper MSVC declines to inline costs twice: stack traffic in the hot loop (vector arguments go
  through a hidden pointer, §6.5) and a call, which fails the lift (§7.2, step 3). The variant
  then is not dispatched in release (DR-008), which becomes an S1/M2 parity failure. So:
  - a kernel-variant TU contains exactly one external-linkage function, the variant entry;
  - every helper it uses, including those in `mith_canon.h`, is `static MITH_FORCEINLINE`
    (`__forceinline` on MSVC, `inline __attribute__((always_inline))` on GCC and Clang);
  - the build fragment makes MSVC warning C4714 (a `__forceinline` function not inlined) an error
    (`/we4714`); GCC already rejects a failed `always_inline`;
  - helpers never pass SIMD vectors across a non-inlined boundary. Non-kernel code that must do
    so uses `MITH_VECTORCALL`;
  - the census (§7.1) and every audit report residual calls per compiler.

  The audit runs on release flags. MSVC `/Od` builds disable all inlining, `__forceinline`
  included, so debug kernel objects are never audited and dispatch only under dev profiles.
- The table is chosen once at load (cpuid plus XCR0), published through an atomic with
  acquire/release, and can be overridden by environment variable [R11 P0 #5]. The code lives in
  `std_platform` (§9).
- **Release profiles register only variants holding `validated(object)` evidence** for the
  compiler that built them (DR-008). Dev profiles may register `tested` variants. A load-time log
  line then names each one.
- The emitter lowers a selected LIR op to one intrinsic. Hand-transliterated intrinsic code (for
  example a port of `quant_avx512.c`) carries `#[lanes(...)]` correspondence annotations, so it is
  checked the same way [P5 §4].

### 6.8 `#line` maps, symbol names and the map file `v0`

- **`#line`.** Each statement group is preceded by `#line N "kernels/q4.mith"` (package-relative,
  forward slashes, so the text is host-independent). PDB and DWARF line tables then point at
  `.mith` lines. There is one canonical form, because checked-in C must be byte-reproducible;
  [07](07-hearth-port.md) covers how this reads in review.
- **Symbol names.** Seam and ABI symbols keep their declared names (`hx_*`, `hearth_*`). The rest
  are `mith__<module path>__<item>` plus a variant suffix for kernels. Names carry **no hash**,
  which would rename every caller on each body edit and turn checked-in diffs into noise.
- **Map file.** A deterministic sidecar `<unit>.mithmap.json` is checked in beside the C. It maps
  each symbol to definition hash, variant, grade and source span. Each build also writes a copy
  keyed by PDB GUID+age or ELF build-id, so profiles and crash dumps find it (§10).

```json
{"symbol":"mith__kernels__q4__q4_row_dot__portable","def":"kernels::q4::q4_row_dot@9c41e2d0",
 "variant":"portable","grade":"exact*cross_device","source":"kernels/q4.mith:19-33"}
```

### 6.9 Reproducible, checked-in C (DR-026) `v0`

- The generated C, `mith_canon.h`, the build fragment and the map files are committed. CMake builds

## 7. The object audit (B1.5): census, lifter, loop correspondence

### 7.1 X0: the instruction census (DR-008) `v0 (M0)`, before the lifter exists

G02's ~105 instruction forms (74 mnemonics, ~10 FP-sensitive) are *implied by the intrinsics* in
Hearth's SIMD files; the census of what compilers emit is its open question 6 [G02 §1].
**Procedure:** compile `quant_avx2.c` and `quant_avx512.c` with MSVC, Clang and GCC at Hearth's
shipping flags, disassemble each kernel symbol with XED, and record per compiler (a) the iclass
histogram, FP-sensitive versus bitwise; (b) control-flow shape: unroll factors, rotation (guard
plus do-while), peeled prologues and tails, spills and reloads, constant-pool loads, and any
residual calls (helpers not inlined, outlined `memset`/`memcpy`); (c) the exact lowering of
`_mm512_reduce_add_ps` (its documented tree equals `sum16`'s final stage, but compiler pairing is
unverified [G02 §6]) and the horizontal shuffles. **Output:** a measured ledger
artifact that fixes the day-one semantics table and the loop shapes the lifter must handle. If it
shows shapes T1 cannot match within the rule budget, X2 still runs on transliterated IR, and the
object audit is re-scoped *before* lifter work is spent.

### 7.2 The lifter `v0 (M2)`

1. **Extract.** Parse the COFF (MSVC) or ELF (Clang, GCC) object. Take the kernel symbol's
   `.text` bytes and relocations. Resolve RIP-relative constant-pool loads, so the values of
   shuffle-control and broadcast constants are known.
2. **Decode** with XED (Apache-2.0) to iclass plus operands [G02 §6].
3. **CFG.** Kernels must lift as **leaf functions with direct branches only**. Any call
   (including a compiler-outlined `memset` or a helper the compiler declined to inline), any
   indirect branch, or any unknown iclass is a lift failure. The forced-inline rule of §6.7 is
   what keeps emitted helpers from producing such calls.
4. **SSA over table semantics.** Model registers, flags and masks. Treat parameter buffers as
   symbolic arrays. Treat **stack slots as cells promoted to SSA values**: a spill followed by a
   reload with no aliasing store in between is an identity. Spills are therefore invisible to
   T1.
5. **Loops.** Recover natural loops and induction variables, then align them with the KIR loop
   nest using the schedule's correspondence map (§7.3).
6. **T1/T2.** At each correspondence point, symbolically execute both sides, hash-cons the FP DAGs
   and compare modulo the audited exact-rewrite list. Integer subterms become T2 obligations
   discharged with certificates. The rule list, including the NaN-order side condition on
   commutation, lives in [03](03-trust.md).
7. **Witness and admission.** The output is a witness: lane map, register-to-value map, loop map.
   `mithcheck` replays it in linear time. The *harness*, not the agent, admits the resulting
   `refines(variant@object, meaning)` claim at grade `validated` ([03](03-trust.md),
   [05](05-agent-protocol.md)).
8. **Failure.** The agent gets the minimal mismatch: lane, block, and the two DAG fragments
   [P5 §7]. The variant drops to `tested` and is barred from release dispatch (DR-008).

The same decode, CFG and SSA stages serve the **T0-bin confinement** check (§1) for
`timing_only` policy and evolve code, `v0 (M4)`. That check enforces an instruction allowlist that
bans RDTSC/RDTSCP/RDPMC/CPUID/LDMXCSR/FLDCW, syscalls and indirect calls, plus stores only to the
state block or stack, plus fuel ([03](03-trust.md)). Its verdict is the `proof`-form evidence
behind `confined` claims, graded as in §1 (effective `validated(partition)` from table premises;
for `confined(S)`, `validated(bounded)` via the store-core theorem; code floor `tested`, printed,
not met). T0-src's verdict on the same code is advisory. One decoder therefore backs two trust
claims.

Bochs, the second oracle for the semantics table, runs only as an external process during fuzzing.
It is never linked into Mithril, because Bochs is LGPL [G02 §9] [inference].

### 7.3 Loop correspondence under unrolling, rotation, peeling and spills

[03](03-trust.md) owns the soundness argument (the lockstep rule: identical initial values plus a
matching one-iteration DAG imply equality by induction, proved once). This section owns the
engineering that brings compiler output into lockstep shape.

| Compiler transformation | How the lifter normalises it | If it cannot |
|---|---|---|
| **Unroll by u** | The map or the induction stride gives u. One lifted body is matched against u consecutive meaning iterations, and the lockstep rule runs on the unrolled pair | unknown → reject |
| **Rotation** (guard plus do-while) | The guard is recognised as the zero-trip test. The body matches the meaning body. Entry values are compared at the guard | reject |
| **Peeling** (alignment prologue, tail) | Peeled iterations are matched as straight-line instances of one meaning iteration. Hearth's fixed 64-element blocks and masked tails keep shapes small | reject |
| **Register rotation / modulo variable expansion** | Removed by SSA renaming | — |
| **Spills and reloads** | Store-to-load forwarding on stack cells (§7.2, step 4) | reject if a spill slot aliases a parameter buffer |
| **Split float accumulators** (reassociation) | Never legal under canon.v1. It shows up as a DAG mismatch | reject: correct behaviour |
| **Integer accumulators reordered or split** | Allowed. T2 proves the polynomial identity under range bounds (`int_assoc`) | T2 unknown → reject |

### 7.4 Witness replay versus re-search

Lifting and matching are expensive; replaying a witness is linear. Release builds always
**replay** witnesses on the *shipped bytes* and search again only when a byte hash changes (§11).
The same pattern covers B4 stencils (holes as symbolic constants with T2 ranges) and agents'
assembly prototypes.

## 8. Cross-compiler and cross-OS variance; arm64 NEON validation

### 8.1 Which compilers must pass `v0`

Each release profile names its **shipping compiler set**:
- `win-x64`: MSVC (Hearth is Windows-first, ADR-0007 [R11 §1]);
- `linux-x64`: whichever of Clang or GCC the Linux release uses;
- `macos-arm64`: Apple clang. This is a CI profile, not a performance target. Generated C must
  build and pass Hearth's tests there from `v0`, because Hearth's CI already covers macOS
  ([07](07-hearth-port.md)); the cross-ISA corpus comparison that grades its kernels is `v1`
  (§8.2). Its kernels can only be `tested` (§8.3), so it cannot carry the exact-kernel
  `validated` claim of DR-021.

**Every dispatched variant built by a shipping compiler must hold `validated(object)` evidence.**
A compiler outside the shipping set produces information, not release evidence. Its binaries
dispatch only the variants it validated, falling back to other validated variants or the portable
path.

**The audit variance matrix** (a Fact Plane view) maps kernel × ISA × compiler × version × flags
→ {validated, unmatched(reason), lift-failed(iclass)}. Each failure is a class-T tombstone with
trigger `compiler_version != <pinned>`, so `mithc revisit` re-audits on upgrade
([06](06-forge.md)). A validated variant that breaks on upgrade with no fix expressible in C is
DR-009's "unpinnable rewrite" signal. GitHub-hosted runners may lack AVX-512 or Zen 5 hardware
[inference]. The audit is static, so CI still earns `validated` evidence for variants it cannot
execute, which tests cannot do. Only semantics-table fuzzing needs Zen 5 silicon, and it runs on
the 9950X outside measurement windows.

### 8.2 Cross-OS output identity `v1`

- **Generated C is host-independent** (`v0`, §3). For a given target, `mithc` on Windows and on
  Linux emits the same bytes. OS differences live only in `std_platform` backends selected by target.
- **Logits.** Once ADR-0010 removes platform libm from the logits path (DR-014), cross-OS bit
  identity becomes *checkable*. UCRT alone switches between FMA3 and non-FMA3 transcendental paths
  at startup, and the two disagree on 44,232 `sinf` inputs (measured [G04]). G04 therefore
  proposes INV-DET-4: logits bit-identical across the supported OS, compiler and ISA combinations.
- **CI** runs the cross-binary hash corpus on Windows/MSVC, Linux/GCC and Clang, and macOS arm64.
  A mismatch is bisected through the corpus's per-kernel entries (matmul outputs across ISA, T and
  row splits [R11 §Staged plan]).
- **Second C compiler.** Non-kernel code is also built with a second x64 compiler and run against
  the same corpus. This N-version compilation is cheap insurance for trusting the C compiler
  (§12).

### 8.3 arm64 NEON validation

- **`v0`/`v1`: portable schedule only.** arm64 builds use the `portable` schedule through C11. FMA
  is baseline on AArch64 and Clang contracts by default, so `-ffp-contract=off` is load-bearing
  there. Apple clang's `sinf`+`cosf` fusion broke Hearth's first macOS run [G04]; exact code calls
  no libm, which removes that class. The §6.2 contraction scan runs over arm64 objects with an
  AArch64 decoder (Arm's machine-readable specification includes encodings [R07 §7]; the choice is
  open). arm64 output is graded **`tested`** by hash-corpus equality with x86 under INV-DET-4. The
  precedent: kimi-k3-in-c reports byte-identical output across Linux and Windows builds using
  scalar-order AVX2/NEON and `-ffp-contract=off` [G03, R06].
- **NEON schedules: `by-trigger`** (ROADMAP D-17, from [P5 §13]: owner priority for macOS
  performance, or hardware availability). Under canon.v1, `sum16` maps to four 4-lane `q`
  registers, which correspondence maps handle like AVX2's two `ymm` [G03]. The arm64 semantics
  table derives from Arm's authoritative machine-readable ASL via Sail/ASLp [R07 §7], which makes
  arm64 the *easier* table. It is still fuzzed on Apple-silicon runners, with an FP-environment
  layer for FPCR (FZ, DN, RMode) and Arm's NaN propagation. Until it exists, NEON variants cannot
  be `validated` and are not dispatched in release.

## 9. Runtime: no hidden runtime, `std_platform`, large pages for a 30 GB arena

### 9.1 What "no hidden runtime" means `v0`

Generated code depends on `std_platform` and nothing else. There is no GC and no unwinding: a trap
ends its fail domain ([01](01-language.md) §12.2); it never unwinds and never aborts the host. At an
`export abi` entry a trap becomes the declared error code, so it never crosses the ABI [P5 §3.4];
traps propagate by status return, never by `setjmp` or unwinding tables. There are no global
constructors; lazy initialisation uses `InitOnceExecuteOnce` or `pthread_once` [R11 P0 #9]. ABI
errors are negative codes. `std_platform` is Mithril code under the `unsafe`/`foreign` grants
(`mith.toml`), emitted as C over OS APIs, a few hundred audited lines per OS [inference, G05].
**M4 gate** ([ROADMAP §5](../ROADMAP.md)): zero user `unsafe` outside `std_platform`, and audited
`unsafe`/`foreign` **≤ 1,500 lines across OSes** [target, P5 M4]. **Kill:** user `unsafe` outside
`std_platform` in > 2 places (amber at 1–2: an audited primitive by ADR), **or** dispatch above
C + 10% that cannot be closed → reopen the memory model [P2, P3, P5]. **Two phases (DR-020).** In
S4–S6a (`v0 (M4–M5)`), `std_platform` binds Hearth's existing `hx_platform.h` functions through
`foreign`, and store *logic* is ported over them, so a platform regression cannot mask a logic
regression [P3 §9]. In S6b (`v0 (M5)`), the native layer replaces
`platform_win.c`/`platform_posix.c` last, because it is the riskiest unsafe surface [G05].

### 9.2 Components `v0` (M4–M5 in the two phases of §9.1; ISA dispatch and the FP guard from M2)

|---|---|---|---|
| `Mutex<T>` with scoped `with_lock(\|s: &mut T\| ..)`, `Condvar` | SRWLOCK, CONDITION_VARIABLE | pthread | Timed waits never return early: re-wait on early expiry; `CLOCK_MONOTONIC` [R11 P0 #12] |
| `Arena` → `SlabBuf` (linear, 4096-aligned), `Arena.split` | `VirtualAlloc`, large pages (§9.4) | `mmap` + THP | Per-chunk uniqueness tracking [G05 §A] |

**FP-environment guard** `v0`. Every T1 certificate assumes default MXCSR (round to nearest, no
FTZ/DAZ), and Hearth never writes or asserts it [G02]. Small regions run on the *caller's* thread
[R11 §3], and a host can have FTZ/DAZ set per thread or process-wide (linking with GCC's
`-ffast-math` is the classic way [inference]), which would otherwise silently break INV-DET-3.
So, under the `fp_env` effect (which no exact code holds):
- every `export abi` and `hx_*` entry, and every thread that executes exact code, **sets** the
  default MXCSR (FPCR on arm64) on entry and restores the caller's value on exit;
- pool workers set and assert the default at start (Hearth constitutional item 7 [P5 §9.2]).

The certificate's "default MXCSR" precondition is therefore checked at entry: a runtime-checked
trust-base entry, not an axiom and not a discharged obligation ([03](03-trust.md) §3.4,
[ARCHITECTURE §6.3](../ARCHITECTURE.md)).

**Hot-swap** `later`: versioned dispatch tables published by release-store at quiescent
token-boundary epochs (`hx_store_tick`), reclaimed through `Frozen` refcounts. No epoch-reclamation
API, no self-modifying code, no INVD or CMPXCHG16B tricks [G05, R09 §6]. Its first consumers,
weight overlays and live policy swap, are post-v1 (DR-025;
[SEED-REFINEMENT §11](../SEED-REFINEMENT.md)), and v0 and v1 choose the dispatch table once at
load (§6.7). The constraints bind now: no code path patches code in place, and B4, if triggered,
swaps code only this way (§5).

**Test builds** `v0`: a loom-style permutation scheduler under `Mutex`/`Condvar` (the deadlocks in
the Rust study were all in safe code [G05 §1]), test-only seams [R11 P1 #23], alias assertions
(§6.4), ASan/UBSan/TSan. **Measurement mode** `v0` (in place for the first gate measured on
Mithril-built code, S1) links the trusted harness: runtime-owned clock, joins of all async work,
poisoned allocations ([06](06-forge.md)).

### 9.3 A snippet

```mith
/// One reservation, split into owned 4096-aligned slabs (G05). The page size actually obtained is
/// reported, never assumed: it enters the environment fingerprint of every measurement on it.
fn open_slots(mem: &MemCap, n_slots: u32, slab: Aligned<u64, 4096>) -> Result<Slots, AllocError>
    uses { alloc(LargePages) }
{
    let arena = Arena::reserve(mem, n_slots, slab, Pages::PreferLarge)?;
    let report = arena.page_report();          // large and small bytes actually committed
    Ok(Slots::new(arena.split(n_slots), report))
}
```

### 9.4 Large pages and TLB behaviour for a 30 GB slab arena `v0 (M5, S6b)`

**What Hearth does today** (from source). `hx_alloc_large(size, 1)` enables
`SeLockMemoryPrivilege` through runtime-resolved `advapi32`, then makes **one**
`VirtualAlloc(MEM_LARGE_PAGES)` call for the whole arena. On failure it falls back **silently** to
4 KiB pages; the only trace is a debug log line. POSIX over-maps a 2 MiB-aligned range and calls
`madvise(MADV_HUGEPAGE)`, which is advisory. The store and dense arenas request large pages; the
KV cache does not. So the full-BF16 run with its 30 GB expert cache has no record of which page
size it ran on.

**Why it matters** (arithmetic [inference], from R11's ~0.96 GB of expert bytes per Qwen3 Q4
token). A token's expert reads touch ~234,000 distinct 4 KiB pages, or ~460 of 2 MiB. A 30 GiB
arena is 7,864,320 small pages or 15,360 large ones. The effect on Zen 5 decode bandwidth has never
been measured, and this design does not guess.

**Design.**
1. **Page size is an environment fact.** `Arena::page_report()` returns the bytes actually
   committed per page size. Each chunk is checked, on Linux through `smaps`-style accounting
   [inference]. The report enters the fingerprint of every measured claim. A run that silently
   fell back is a different environment, so its numbers never pool with large-page runs
   (INV-HONEST).
2. **Chunked reservation.** The arena is reserved as chunks of a whole number of slabs, each
   rounded up to a 2 MiB multiple. Waste is under 2 MiB per chunk. One all-or-nothing request
   becomes graceful degradation when free 2 MiB frames are fragmented after uptime [inference].
   Slabs never straddle chunks. `Arena.split` hands out per-chunk owned `SlabBuf`s with per-chunk
   uniqueness counts [G05 §A].
3. **Privilege is an Owner decision.** Granting "Lock pages in memory" is a Windows security
   setting. The toolchain never changes it; it reports whether the privilege is held. Large pages
   are non-pageable, so a 30 GB locked arena on a 64 GB box is a capacity decision. `mithc
   explain` shows it next to the dense arena and the KV cache.
4. **A pre-registered measurement** (S4/S6b, run by [06](06-forge.md)'s protocol):
   - arms: large pages versus forced small pages;
   - metrics: decode tok/s and expert-matvec GB/s;
   - configurations: a 30 GiB in-RAM cache and 2/4/8 GiB NVMe-bound caches; also open latency;
   - procedure: interleaved, load-gated, ≥ 10 runs per arm, e-value reported.

   The result becomes a ledger fact, or a class-H tombstone such as "no measurable effect (Zen 5,
   Win 11, 2.39 MiB slabs)" with trigger
   `slab_bytes != at_burial.slab_bytes || cpu != at_burial.cpu` ([06](06-forge.md) §7.2 grammar).
5. **macOS** uses base pages only (a CI target, not a performance target, §8.1). On Linux, THP is
   attempted and reported.

**Observations for [07](07-hearth-port.md)** (not defects):
- the silent fallback;
- the single all-or-nothing reservation;
- the KV cache not requesting large pages. At 4K context it is about 0.40 GB per token
  [P3 §6, inference].

## 10. Debugging and profiling

**Debugging** `v0`. Generated C is built with debug information (MSVC `/Zi` → PDB; Clang → DWARF,
or CodeView/PDB as `clang-cl`). Through `#line` (§6.8), breakpoints and stepping work on `.mith`
lines. C locals keep their Mithril names, suffixed only for shadowing. An out-parameter result
shows as `*out`; the map says so, and a later agent-facing debugger adapter renders it as the
return value. Crash dumps resolve symbol → definition hash through the build-keyed map, so a report
names `store::evict::victim@3fa09c1e`, not a C line.

**Profiling** `v1` (profile ingestion; `mithc explain` itself is `v0 (M2)`). Windows has no
`perf_event_open` [panel: systems]. There are two sources:
**ETW** sampled profiles with stack walks, from Windows Performance Recorder, resolved through the
PDB [inference: kernel sampling needs elevation; the Owner runs it]; and **AMD uProf** on Zen 5
for counter- and instruction-based sampling [inference: verify Windows IBS support at M2]. Their
per-symbol and per-address tables are **ingested by `mithc explain --profile <file>`**, so no new
verb is needed. `explain` maps samples to definition hash, variant and `.mith` line, puts
per-definition time beside the cost signature's floor and fraction of roof ([02](02-compute.md)),
and attributes the residual: bandwidth, latency, stalls, check tax (§6.6), copies (§6.5). Linux CI
runners usually lack PMU access [inference], so profiling is a desktop activity.

**Evidence status.** Profiles are `measured` but *diagnostic*. Promotion-grade claims come only
from the sealed harness with its runtime-owned clock (DR-018, [06](06-forge.md)). A profile can
explain and can feed tombstone triggers through gap attribution; it cannot promote.

## 11. Edit-loop and CI latency budgets; caching audited objects

A 200 ms check target means nothing if every kernel edit then waits on MSVC plus an audit
[panel: systems]. The loop is therefore split into tiers. Each tier has its own budget and its own
cache. Budgets are [target] until M1/M2 replace them with measured p50/p95, recorded as ledger
facts about `mithc` itself (§13).

| Tier | What runs | Budget [target] | Source |
|---|---|---|---|
| **L0 check** | One-definition edit, warm `mithc serve`, Hearth-sized corpus (~9k lines): parse → THIR, fact delta, diagnostics | p50 ≤ 200 ms, p95 ≤ 1 s | [P1 §4] |
| L0 hole | `mithc hole` | ≤ 100 ms | [P1 §4] |
| L0 at scale | One-definition re-check in a 30k-line package | < 300 ms | [P5 §4] |
| **L1 test** | Affected tests run under `mithi` (no C compilation): property tests, small corpus | ≤ 10 s | this doc |
| **L2 prove** | `mithc prove <kernel> --target t`: schedule → LIR → T1/T2 before compilation; cache miss | ≤ 30 s per variant | this doc |
| **L3 audit** | `mithc audit <kernel>`: emit → compile one TU with the pinned compiler → lift → T1, on a byte-hash miss | ≤ 120 s per variant | this doc |
| L3, cache hit | Witness replay on unchanged `.text` bytes | ≤ 1 s per variant | this doc |
| **L4 PR CI** | Regenerate the C byte for byte; build ×3 OS; flag audit; contraction and copy scans; C tests; goldens; hash corpus; audits of *changed* variants only | ≤ 30 min | this doc |
| **L5 nightly** | Full re-audit of all variants × compilers; semantics-table fuzz on the 9950X (quiet-window rules, [06](06-forge.md)); mutation runs; `mithi` differential at scale | overnight | this doc |

**Caching audited objects by closure hash** `v0`. The key is §3's audit key (closure, schedule,
target, toolchain hash, compiler identity, flags). The value is the kernel symbol's `.text` byte
hash plus witness and certificates; hashing symbol bytes, not whole objects, keeps COFF timestamps
and debug sections out. On a hit the build recompiles (cheap). Identical bytes mean the witness is
**replayed**, not searched. Different bytes under an identical key mean a nondeterministic
compiler: the case is recorded, re-audited, and counts against that compiler pin. Witnesses and
certificates are content-addressed blobs in the data directory; admitted facts live under
`.mith/ledger/` (DR-019). A fresh clone reuses validations, never measurements. Measurement never
runs on shared CI runners ([06](06-forge.md)).

## 12. Assurance for non-kernel emitted C

The store, parser, pool, API and forward-pass glue are control-heavy. **No translation validation
is planned for control-heavy code.** For non-kernel code, the C compiler is in the trust base
[P5 §5.1]. What stands in its place, in order of strength:

1. **Format-derived parsers** (S2). The `format` description generates a parser and writer with
   no `unsafe`. Its gate: identical accept/reject decisions and parsed configurations against C on
   ≥ 10^6 generated files [inference, P5 S2]. Totality and safety (INV-FMT/SAFE) are graded
   `tested`: fuzzing, the `mithi` differential and the golden malformed-file test. Only the bounds
   obligations that T2 discharges are graded `proof`, at source level. The parser is generated by
   an untrusted `mithc`, checked by a front end graded `tested` (DR-010) and compiled by a C
   compiler that stays trusted for control-heavy code, so no stronger claim is made
   ([ROADMAP §7](../ROADMAP.md) B1). It is still the strongest item here for the most
   attack-exposed code.
2. **Front-end guarantees** (T0-src): types, effects, capabilities, ownership, second-class
   references. For example, the `hx_store_heat` pointer race cannot be expressed [G05 §1]. These
   are graded `tested` until mechanised (DR-010).
3. **`mithi` differential testing.** Generated inputs run through compiled C and through `mithi`
   in independent mode, and value results are compared bit for bit (canonical NaN). Effectful code
   runs against a deterministic, recording `std_platform` mock, and the traces of platform calls
   are compared [inference]. This is the main defence against bugs in `mithc`'s lowering and the C
   compiler.
4. **Hearth's oracles:**
   - the unchanged C test suites linked into the mixed build;
   - the golden suite;
   - the cross-binary hash corpus, byte-identical to `hearth-c-ref` on the same OS, CRT and ISA
     [R11 §Staged plan].

   For logits-path non-kernel code this is the admissible evidence: `tested` plus the hash corpus,
   labelled as such (DR-021).
5. **N-version C compilation.** Non-kernel code is built with two compilers and run on the same
   corpus (§8.2).
6. **Sanitizers and schedulers:** ASan, UBSan and TSan on generated C (Hearth has no TSan job yet
   [G05 §Hearth 1]), the loom-style permutation scheduler, alias assertions, and the chaos suite
   for the store core ([02](02-compute.md)).
7. **Binary scans:** contraction (§6.2), hidden copies (§6.5), and T0-bin confinement for
   policies (§7.2).

The lesson from Csmith and CompCert applies: bugs migrate to the unverified periphery [R07 §2].
Differential testing is therefore aimed at the emitter, not at the parts already checked.

## 13. How `mithc` is built and checked by agents

**Shape** `v0`.
- **Crates by layer:** `mith-syntax`, `-hir`, `-thir`, `-mir`, `-kir`, `-lir`, `-emit-c`,
  `-audit`, `-facts`, `-ledger`, `-serve`, `-cli`. **`mithi`** is a separate crate that shares
  nothing with lowering.
- **The trusted core is separate crates with no dependency on `mithc`:** `mithcheck` (T1/T2
  replay), the semantics table and generator, the gate, the measurement harness. They read only
  serialised certificates [P5 §5.1] and are built by a **frozen bootstrap toolchain pinned by
  hash**; a candidate `mithc` never builds them. Updating the bootstrap is an Owner F0 change
  needing diverse double compilation [P2 §4, P4 §8.8].
- **Budgets** [inference, P5 §2]: compiler 35–50k lines, protocol 2–4k, checker ≤ 4k, table
  1.5–3k, ledger 2–3k ([03](03-trust.md) owns the TCB inventory).
- **Rust practice:** `#![forbid(unsafe_code)]` in every `mithc` crate; pinned toolchain and
  committed `Cargo.lock`; a shallow crate graph, so a typical agent edit rebuilds at most two crates
  [target]. Rust compile times are the price of choosing Rust [R09 §9].

**The protocol, dogfooded.** Roles apply to the compiler repository as to Hearth
([03](03-trust.md)):
- *Authors* own executable specs of compiler properties; the §6 rules become Fact Plane rules and
  binary-scan checks.
- *Builders* edit crates.
- *Adversaries* own the compiler's mutant pools and the planted-wrong-kernel corpus.
- The *Gatekeeper* is code.

The ledger records evidence about `mithc` itself, keyed by its crate closure hashes: tests,
mutation scores, latency against §11, determinism and fuzz campaigns. Handovers come from the
toolchain journal. The friction rule and `abandon` apply ([05](05-agent-protocol.md)).

**Test layers:**
1. Unit tests and diagnostic snapshots (stable codes and SARIF are agent interface).
2. Lark conformance [P5 §3.1].
3. **`mithi` differential** on every corpus program.
4. **"mithsmith"**, a Csmith-style generator of well-typed Mithril programs. It drives `mithc` and
   all three C compilers against `mithi`, after Csmith's record against unverified peripheries
   [R07 §2] [inference: new work].
5. T1 on every kernel variant, as a backstop for lowering bugs where they matter most.
6. Determinism and host-independence (§3).
7. Cold-agent harness and Mithril MultiPL-E runs ([05](05-agent-protocol.md)): can agents *use*
   what the compiler produces?

Rust suits agents: a large corpus, salsa, and types that catch mistakes at compile time
[R09 §9]. Its arena-and-index IR style is the same shape Mithril's second-class references force.
**F2** (the compiler-heuristic Forge) waits until after the port, with held-out shapes on two
microarchitectures and translation validation in CI (DR-016). An evolved heuristic chooses among
certified rewrites, so it can make code slower, never wrong [P4 §8.8].

## 14. The self-hosting decision

**Decision (DR-026):** `mithc` stays in Rust through the port and Edition 1. Self-hosting is
decided only after M7. Self-hosting before the port is a non-goal [P5 §11.1], [R09 §9].

**Why wait.**
1. **No evidence yet.** Until M7, nothing shows agents maintain Mithril at least as well as Rust.
   Moving early would stake the compiler's maintainability on an unproven claim.
2. **A compiler is a different workload.** It is string-, map- and graph-heavy, with error
   recovery, and v1 has no `dyn`, no macros and only static-dispatch traits (DR-005). Whether that
   suffices is empirical.
3. **Trusting trust.** A self-hosted `mithc` compiles its successor. F0 stays outside that loop
   regardless, built by the frozen bootstrap.
4. **Rust is the fallback anyway.** If DR-017's kill fires, Mithril becomes tooling over Rust and
   C, and a Rust `mithc` is already in place.

**How it will be decided** (at M7; a design-level tombstone in [DECISIONS](../DECISIONS.md)). Port
one self-contained component, the C emitter or the Fact Plane evaluator, into Mithril. Run a sealed
suite of compiler-maintenance tasks on both versions against the B2-style bar: VP@1 ≥ Rust − 3
points, cost ≤ 1.2× [P5 §9.1]. Compare defect escapes under the same differential tests. Trigger
(provisional): `milestone(M7) == passed && component_experiment == noninferior`. Even on success,
F0 is unchanged, and migration goes crate by crate behind the certificate boundaries, each step
gated by `mithi` differential tests and byte-identical C. Failure leaves a class E or V tombstone
that `mithc revisit --design` can re-open ([06](06-forge.md)).
